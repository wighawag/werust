# The macOS type-check harness's stand-in core drifts behind the real one, and nothing catches it

Spotted 2026-08-04 while building `shortcuts-and-mouse-history-buttons-on-the-macos-edge`.

`docs/spikes/macos-wkwebview-renderer-backend/typecheck-macos-from-linux.sh` builds a scratch workspace with a hand-written stand-in `werust-core` (to keep `ring` out of the cross-compile graph) and checks the REAL `crates/desktop-paint` against it. That stand-in had fallen behind: `desktop-paint` imports `load_spinner_visible`, `reload_stop_control`, `ReloadStopControl`, `trust_pin_action_visible`, `trust_pin_action_label` and `trust_pin_detail`, none of which the stand-in carried, so the harness failed to compile on `main` with six `E0432`s before this task touched anything. I added the missing stand-ins so I could use the harness (this task's only local check of the AppKit half), which is a repair, not a fix for the underlying problem.

The underlying problem: the harness's own guard (`crates/macos-renderer/tests/typecheck_harness_guard.rs`) stubs `cargo` out, so it proves the scratch workspace is ASSEMBLED (and that its symlinks resolve) but never that it COMPILES. Nothing on the ordinary gate notices when a core function lands and the stand-in does not grow it, so the harness rots quietly and the next macOS agent discovers it — exactly the round trip the harness exists to prevent. Two shapes worth weighing: a guard that greps the real `desktop-paint`'s `use werust_core::{…}` list against the stand-in's public items, or dropping the stand-in for the real core once whatever keeps `ring` out of the graph can be solved another way.
