## Open questions

This is an EXPLORATION task: its first job is to answer these, not to ship a subsystem blind.

1. **Retrieval tier — pick the cheapest that is genuinely trustless (NO IPFS node required for tiers 1-2).** Research (2026-07, primary sources below) already maps the landscape; the exploration's job is to CHOOSE a tier and prove it, not re-derive it:
   - **Tier 1 — CAR over HTTP from a TRUSTLESS gateway (the sweet spot, no node).** The [Trustless Gateway spec](https://specs.ipfs.tech/http-gateways/trustless-gateway/) lets a light client fetch `GET /ipfs/{cid}?format=car` (or `Accept: application/vnd.ipld.car`) and get back a **CAR stream = the raw DAG blocks**, NOT the gateway's reassembled bytes. Each block is self-identified by its CID, so the client VERIFIES each block against its own CID and reassembles the file/directory LOCALLY — the gateway is untrusted (exactly werust's model). `dag-scope=entity` + `entity-bytes=from:to` fetch only the blocks needed for a file / byte range (so a large site is not a full download). Public trustless gateways include `dweb.link` and `trustless-gateway.link`. This stays over the existing sync `Fetcher`/`ContentSource` seam (plain HTTP GET returning a CAR byte stream) — NO node, NO async runtime required. The Rust crate **`rs-car-ipfs`** (wraps `rs-car`) already does "read files from IPFS trustless gateways" with per-block verification (`read_single_file_buffer` / `read_single_file_seek`) — a bind-a-vetted-crate path, not hand-rolled DAG walking. (`@helia/verified-fetch` is the JS reference implementation, useful as a semantics oracle.) DEFAULT RECOMMENDATION unless a blocker is found.
   - **Tier 2 — delegated routing + trustless gateways (still no node).** Helia's model: an HTTP delegated router (`delegated-ipfs.dev`) finds providers, then CAR-fetch from trustless gateways. More resilient than a single hard-coded gateway; still pure HTTP, no node. A follow-on hardening of tier 1.
   - **Tier 3 — embed a libp2p/Bitswap client (real p2p, NO gateway, but heavy + async).** `iroh`/`beetle`, `rust-ipfs`, or `ipfs-embed` let werust speak the IPFS network directly with no gateway at all (your "hook into the network and fetch" idea) — genuinely trustless at the transport, but pulls in an async libp2p stack, peer routing, and connection management. It wants the async runtime Phase-2 (Helios) is already introducing, so it FOLDS INTO the Phase-2 async trustless story rather than gating this task. Do NOT build tier 3 to unblock multi-block rendering; tier 1 already does that.
   - DECIDE: which tier ships in THIS task (recommend tier 1), and does it stay behind the existing sync `Fetcher` seam (yes for tier 1-2) or wait on the Phase-2 async path (tier 3)?
2. **DAG + UnixFS scope.** Confirm the vetted crates for CAR parse + `dag-pb` block decode + UnixFS reassembly + per-block CID verification — start from `rs-car-ipfs`/`rs-car` and the `cid`/`multihash` crates the repo already uses (bind, don't hand-roll — `docs/adr/0001`); evaluate them against a real fixture before committing. Which UnixFS features are in scope (chunked files, directories with `index.html` resolution, HAMT-sharded directories, symlinks)? What is explicitly out? (The Trustless Gateway spec's client obligations — "verify CAR completeness; treat an incomplete stream as a retrieval FAILURE" — map directly onto werust's fail-closed stance.)
3. **Trust + failure model.** How does a partial/hostile DAG fail (a block that does not hash to its CID, a missing block, a malicious link) — always fail-closed with a distinct reason? How large a site do we retrieve before refusing (a size/time budget)? Does this fold into the Phase-2 trustless story, or stand alone?
4. **Path-aware rendering + codec discrimination (a real site is a DIRECTORY, and the current path is single-block-and-ignores-path).** A real `.eth` site (e.g. `mandalas.eth`) is a UnixFS DIRECTORY dag-pb CID, not a file: rendering it means resolving the directory to its `index.html`, THEN serving every relative sub-resource the page requests (`ipfs://<cid>/style.css`, `/app.js`, images) — each its own path-scoped lookup INTO the verified DAG. The current `werust_core::ipfs::resolve_ipfs_request` fetches a SINGLE verified block per CID and IGNORES the path (its own docstring says so); `parse_ipfs_uri` already parses `ipfs://<cid>/path` but the path only informs MIME today. DECIDE how path resolution works over the verified DAG (walk `dag-pb` directory links / UnixFS `entity-bytes` per sub-resource) so a directory site actually renders. AND: discriminate by CODEC, never by catching a hash error — a `raw`/leaf (0x55) CID that fails to hash is a HARD fail-closed tamper signal and must NEVER be served unverified; a `dag-pb` (0x70) CID is handled by the DAG-verify path. (This subsumes the review findings that killed the interim gateway-fallback task: the cheap `⚠`-served interim was not actually cheap — it needed this same path routing — and catching `HashMismatch` to serve bytes anyway would have been a security hole. So there is no interim; this task is the ONE fix, done verified.)

## What to build

The REAL, honest fix for multi-block IPFS sites: retrieve and byte-verify a UnixFS `dag-pb` DAG so a real site (directory/chunked file) can be legitimately `ContentVerified` — verifying EACH block against its own CID and reassembling the content LOCALLY, rather than trusting a gateway's reassembled bytes, AND resolving directory + sub-resource PATHS so a real multi-file site actually renders. This is the SOLE fix (there is no `⚠`-served interim: an adversarial review found the interim was not actually cheap — a directory site needs the same path routing this task builds — and that serving bytes on a hash error would be a security hole, so the interim task was dropped). Landing this lets an ENS-resolved multi-block site carry the honest `NameViaTrustedRpc` (content-verified, name via trusted RPC) posture, and a plain `ipfs://` directory the `ContentVerified` posture — legitimately, because every block was checked.

As an exploration task, produce: the answered open questions (a short findings/ADR), a prototype or spike proving the DAG-walk + per-block verification works against a real fixture site offline, and either the shipped verifier behind the existing seam OR a precise follow-on task set if the work is larger than one task. Wire it so the desktop and (via `mobile-ipfs-scheme-interception-ios-and-android`) mobile `ipfs://` paths can upgrade a multi-block site from `⚠ unverified` to genuinely `ContentVerified` once this lands.

- [ ] Tests are network-isolated (CAR/block fixtures, loopback, no live gateway) and mirror the repo's test style.

Trustless retrieval fetches a CAR (`?format=car`) or raw blocks (`?format=raw`) so verification happens client-side. NO IPFS NODE is required for the recommended path: a trustless gateway serves the raw DAG blocks over plain HTTP and the client verifies them — see the tiered analysis in the open questions.
