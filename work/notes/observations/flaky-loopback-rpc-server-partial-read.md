# Flaky loopback RPC-server test: single-`read()` can miss the request body

2026-07-22 — While running `cargo test -p werust-core --lib` for the bare-`.eth` front-door task, `ethereum::tests::end_to_end_eth_call_over_the_bound_transport_off_the_network` failed once ("the received request body was json: EOF while parsing a value") then passed on every retry (3/3 in isolation, 3/3 full suite). The loopback `LocalRpcServer` (and the sibling `SequencedRpcServer` in `ens.rs`, and `LocalGateway` in `ipfs.rs`) capture the request body from a SINGLE `stream.read(&mut buf)` and assume the whole HTTP request (headers + body) arrives in that one read; under parallel test load the body can land in a later packet, leaving the captured body empty and the `serde_json::from_slice` assert panicking. Not my task's code; captured for whoever hardens these harnesses (loop the read until the `Content-Length` body is drained).

2026-07-23 (harden-loopback-test-servers-drain-request-body) — RESOLVED. Added a shared race-hardened reader `crate::loopback_test_server::read_request_body` (in `crates/werust-core/src/lib.rs`) that loops `read()` until the `\r\n\r\n` header terminator is seen AND the full declared `Content-Length` body is drained, then returns the body bytes. Both loopback fixtures now reuse it: `LocalRpcServer` (`ethereum.rs`) and `SequencedRpcServer` (`ens.rs`). NOTE on the premise: `ipfs.rs` no longer has a `LocalGateway` (or any) loopback HTTP fixture — its tests are pure `parse_ipfs_uri`/decoder tests with no TCP server — so there was no third copy to fix; the shared helper still lives crate-wide for any future gateway fixture to reuse. A segment-split regression test (`drains_a_body_that_arrives_in_a_later_tcp_segment`) locks in the fix; 15 full `cargo test` sweeps + 40 high-parallelism runs of the two affected tests were green with no EOF panic.
