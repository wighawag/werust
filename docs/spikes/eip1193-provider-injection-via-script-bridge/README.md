# Spike: EIP-1193 provider injection via the script-message bridge

Durable design record for task `eip1193-provider-injection-via-script-bridge` (spec `rust-successor-ship-webview-and-reach-t1-on-pure-rust-stack`, story 5; one of the two trust hooks that qualify a backend).

## What was built

A native **EIP-1193 provider** is now injected into pages over the `Renderer` seam's script-message bridge, and a page-side `request({ method, params })` call round-trips across the bridge to a native handler and back — with NO keys involved.

- **`crates/renderer/src/lib.rs` — the seam's response half.** Added `Renderer::evaluate_javascript(&self, script)` (default no-op): the browser -> page push that completes the bridge. The pre-existing `register_script_message_handler` carries page -> browser; `evaluate_javascript` delivers the answer back into the live page. Implemented on the WebKitGTK backend via `webkit6`'s `WebView::evaluate_javascript` (`crates/webview-renderer/src/backend.rs`).
- **`crates/werust-core/src/provider.rs` — the toolkit-free provider core.**
  - `provider_shim()` — the page-side JS injected at document start: installs a detectable `window.ethereum` (`isWerust: true`) exposing the standard EIP-1193 `request(...)` Promise interface and the event-emitter surface (`on` / `removeListener` / `emit` over `connect` / `disconnect` / `chainChanged` / `accountsChanged` / `message`). Each `request(...)` is assigned a correlation id, parked in a pending map, and posted as a JSON envelope up the bridge; it settles when the native side pushes `window.werustProvider.__resolve(id, result)` / `__reject(id, error)`.
  - `ProviderBridge` — the native handler: `parse` an envelope, `answer` it with a **read-only, keyless stub** (`eth_chainId` -> `0x1`; `eth_accounts` / `eth_requestAccounts` -> `[]`; anything else -> EIP-1193 `4200` unsupported), and `handle` end-to-end into the response-delivery JS (`resolve_script` / `reject_script`).
  - `route_provider_message` — the pure routing a live backend calls per bridge message; `inject_provider_shim` — the shim-injection half exposed on `&mut dyn Renderer`.
- **`crates/webview-renderer/src/backend.rs` — the real end-to-end wiring.** `WebViewRenderer::install_provider()` injects the shim, registers the `werustProvider` script-message handler, routes each posted envelope through `ProviderBridge`, and pushes the answer back by evaluating the settle-call JS in the live page (capturing a cloned `WebView` so the push runs on the GTK loop).
- **`crates/werust/src/main.rs` — day-one product.** The shell installs the provider on the webview backend before wrapping it, so every page the browser opens sees the native provider.

## Why the response push is wired at the webview backend, not behind `&mut dyn Renderer`

The seam's `ScriptMessageHandler` is `Box<dyn FnMut(..) + Send>`. The response push needs a handle to the backend to evaluate JS on its own loop, but a webview is `Rc`-shared (single GTK thread) and therefore NOT `Send`, so the handler closure cannot capture it. The webview backend instead captures a cloned `WebView` (a refcounted GObject handle) directly in its GTK `script-message-received` signal closure — which is not bound by the seam's `Send` requirement — and evaluates there. `werust-core` therefore exposes the pure, `Send`-free pieces (`ProviderBridge`, `route_provider_message`, `provider_shim`), and the backend-specific push lives where the backend lives. The headless seam test `eip1193_provider_request_round_trips_across_the_bridge_seam` reproduces the same routing with an `Arc<Mutex<_>>` sink to pin the round-trip display-free.

## Tests (the proof)

- `crates/werust-core/src/provider.rs` (headless): shim exposes a detectable EIP-1193 surface; envelope parse (well-formed / omitted-params default / malformed rejected); `eth_chainId` and `eth_accounts` stubs answer keylessly; unsupported method refused with `4200`; `handle` round-trips a request to a `__resolve` push and an error to a `__reject` push; `route_provider_message` answers only the provider channel.
- `crates/webview-renderer/src/lib.rs` (headless): `eip1193_provider_request_round_trips_across_the_bridge_seam` (inject shim + register handler + deliver a page `eth_chainId` envelope + assert the settle-call was pushed back through the seam), `evaluate_javascript_pushes_into_the_page_over_the_seam`, and (ignored, display-bound) `real_webview_installs_the_eip1193_provider`.

All non-ignored tests run headlessly and pass under `verify` (`cargo fmt --check && cargo clippy && cargo build && cargo test`).

## Decisions

- **New seam method `Renderer::evaluate_javascript(&self, script)` (default no-op).** The landed seam had no browser -> page response push for a live page (the task's forward-pointer flagged this as a deliberate hand-off). Chosen: add `evaluate_javascript` on the trait, `&self` (real backends evaluate through an interior-mutable handle) and fire-and-forget (async on the backend loop, no result), with a no-op default so fixed-subset native backends with no live JS document are not forced to implement it. Alternative considered: a typed request/response method pair on the trait (e.g. `respond_to_script_message(id, result)`). Rejected: it would bake the EIP-1193 correlation-id protocol into the seam, but the seam should stay transport-neutral (the ipfs:// hook and any future bridge user reuse a generic JS-eval push, not a provider-specific one). TOUCHES: every `Renderer` impl (all pick up the default); the ipfs:// task and the benchmark-harness task may reuse `evaluate_javascript`. Documented at the choice site (the `evaluate_javascript` doc comment in `crates/renderer/src/lib.rs`).
- **The read-only stub reports chain id `0x1` (mainnet) and empty accounts `[]`; every other method (in particular any signing) is refused with EIP-1193 `4200`.** These are user-visible provider defaults. Rationale: the task requires a benign, keyless method demonstrating the full round-trip; `eth_chainId -> 0x1` is the standard detectable read, and `eth_accounts -> []` truthfully reports "no keys held here" (the wallet-broker key-custody model is DEFERRED to the exploration spec `rust-successor-native-renderer-architecture-benchmark`). Refusing everything else keeps the surface honestly keyless rather than silently stubbing signing. Alternative considered: return a fake account address. Rejected: it would imply key custody this task explicitly does not implement. This is reversible: the real method set + a broker arrive with the deferred wallet model. Documented at the choice site (`ProviderBridge::answer`, `STUB_CHAIN_ID` in `crates/werust-core/src/provider.rs`).
- **The provider core lives in `werust-core` (a `provider` module), not a new crate; the backend-specific push lives on `WebViewRenderer`.** Rationale: `werust-core` is "the Rust core" (`CONTEXT.md`) — toolkit-free, seam-driven logic testable at the `dyn Renderer` boundary — which is exactly the provider transport's shape. `webview-renderer` gains a `werust-core` dependency (no cycle: `werust-core` depends only on `renderer`). Alternative considered: a standalone `provider` crate. Rejected as crate-proliferation for one cohesive module. TOUCHES: `webview-renderer/Cargo.toml` (new dependency).

## Coherence check

`EIP-1193 provider`, `trust hooks`, and `script-message bridge` reuse the existing `CONTEXT.md` glossary terms verbatim; the provider is wired as a first-class capability over the seam (the thesis, `docs/adr/0001`), not an extension. The new names introduced — `evaluate_javascript` (seam), `ProviderBridge` / `provider_shim` / `PROVIDER_BRIDGE` / `route_provider_message` (provider core) — do not re-mean any existing term: `evaluate_javascript` is a new transport-neutral seam capability at the same layer as the other bridge methods, and the provider names sit inside a dedicated `provider` module. Key custody is deliberately NOT introduced here (deferred, per the spec's Out of Scope).
