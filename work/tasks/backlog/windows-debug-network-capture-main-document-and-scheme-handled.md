## What to build

Close the other capability the `windows` parity column had to mark `stubbed`: `debug-capture-console-and-network` in `docs/platform-capability-matrix.toml`.

The CONSOLE half is real on Windows and was watched working on a `windows-latest` runner (the shared `console_shim` on the dedicated `CAPTURE_BRIDGE` channel, a page's own `console.log` reaching a rendered list-view row). The NETWORK half is not: the Windows window installs the SHARED `desktop_paint::install_debug_capture`, whose only network capture point is the best-effort injected `network_shim` — the `fetch`/`XHR` calls the PAGE makes and nothing else. So the Windows Network tab has NO main-document row, and no row for the `ipfs://` / `werust://` requests werust's own scheme handler serves. That row's description explicitly names the main-document entry (it must mirror the load's own two-axis posture so the Network tab can never contradict the chrome's trust indicator, `docs/adr/0006`), so the capability is genuinely short here.

Unlike WebKit, this is NOT a platform limit: WebView2 exposes the reach. `crates/windows-renderer` already owns a `WebResourceRequested` handler that sees every request on a registered scheme together with the `SchemeResponse` it answers with (status, mime, size, and whether the verifying route marked it content-verified), and it already observes the main-frame navigation lifecycle (`NavigationStarting` / `ContentLoading` / `NavigationCompleted`). Beyond that, `AddWebResourceRequestedFilter("*")` widens the same event to EVERY request, and the DevTools protocol (`CallDevToolsProtocolMethod` + `Network.*` events) is a third option. Both spike READMEs name the first two as deliberately unwired follow-ons; this task decides between them and wires one.

Constraints that matter more than the wiring:

- **A wildcard filter OVERLAPS the existing per-scheme ones, and the handler ANSWERS requests.** WebView2 raises the event once per MATCHING filter, so the backend deliberately registers ONE non-overlapping filter per registered scheme to avoid a double delivery and therefore a double answer. Adding `AddWebResourceRequestedFilter("*")` beside them re-introduces exactly that. Either collapse to a single wildcard filter whose handler leaves a non-werust scheme entirely alone (it already returns without setting a response for an unrouted scheme), or keep the per-scheme filters and get the capture from somewhere that does not overlap. Whichever you choose, say why, and prove no request is answered twice.
- **Capture is READ-ONLY observation.** It must not alter the load path, the `ipfs://` verification, or any posture, and it must not answer or delay a request. The `ipfs://` route runs behind a real `GetDeferral` on the ADR-0008 off-thread boundary; a capture push is a bounded ring-buffer insert and must stay one, never something the deferral waits on.
- **Derive nothing at the edge.** The per-request posture comes from the core's `request_trust_posture`, in the trust indicator's exact vocabulary. WHICH row is the main document is a decision the codebase has already made twice: desktop, macOS and iOS use the core's ONE main-frame predicate (`BrowserShell::is_main_frame` over the `_redirects` sink), while Android uses its platform's native answer (`WebResourceRequest.isForMainFrame`). WebView2 has a native-ish answer too (`COREWEBVIEW2_WEB_RESOURCE_CONTEXT_DOCUMENT` on the request's `ResourceContext`). Pick one, record which and why (`docs/spikes/debug-console-network-capture-per-platform/DECISIONS.md` Decision 5 is the precedent), and do not invent a per-edge URL compare.
- **Do not silently widen the macOS edge.** `install_debug_capture` lives in the SHARED `crates/desktop-paint` and the AppKit window consumes it. The Windows-specific capture points hang off the Windows backend; if any part is genuinely shared, keep `desktop-paint` a CARRIER (no new derivation) and say what you moved. macOS has the analogous gap with different platform hooks and owns it via `macos-debug-network-capture-main-document-and-scheme-handled` — do not fix it here by accident, and do not leave the macOS edge worse than it was.
- **Say honestly what the chosen reach does and does not see.** If the wildcard filter really does see `<img>`/`<script>`/CSS `url()` on Windows, that is a REAL difference from macOS/iOS (whose subresource limit is accepted by the spec's Out of Scope) and belongs in the matrix row and the spike, not left implied. If it does not, record what it misses.

## Acceptance criteria

- [ ] After a load on Windows, the debug view's Network tab shows a MAIN-DOCUMENT row carrying the load's own two-axis trust posture (the same posture the chrome's trust indicator shows for that load), and it can never contradict the indicator.
- [ ] Requests the Windows scheme handler serves (`ipfs://`, `werust://`) appear as rows with their honest per-request posture, method, status, mime and size, derived by the core's existing rules — no new per-edge trust or row rule.
- [ ] No request is delivered (or answered) twice as a result of the new capture reach, and the `ipfs://` route's deferral is not delayed by capture; covered by a test or a stated, checkable argument in the repo's style.
- [ ] Capture stays read-only: no change to what loads, what verifies, or what posture is reported.
- [ ] The wiring is covered on the Ubuntu `verify` gate (unit tests over the seam/fake plus the source-shape guards `crates/windows-renderer/tests/windows_backend_shape.rs` / `crates/werust-core/tests/debug_capture_edge_wiring_shape.rs` in their existing style), and the `windows-renderer` leg's `window_smoke` asserts a main-document row really appears after its real hash-verified load.
- [ ] The macOS edge is not regressed or silently changed; if shared code moved, the change says which edges it touches and why.
- [ ] The `debug-capture-console-and-network` row's `windows` cell flips from `stubbed` to `implemented` in the same change, naming what proves it and stating the chosen reach's real coverage limit; the parity guard stays green with no weakening.
- [ ] `cargo fmt --check && cargo clippy && cargo build && cargo test` green.
