## Non-blocking review findings

The PR/code review gate (Gate 2) APPROVED 'macos-spike-doc-accuracy-and-harness-guard' but raised the
following non-blocking findings (nits). They do not block integration; this
is their durable home for triage — promote-to-task / keep / delete.

- The two branches of the new guard test are mutually exclusive, so on any ordinary host (including this gate, where HOME is outside every temp root) only the REFUSAL path executes. The ALLOW path, and with it the entire repaired body of the harness, is never run by the gate: the second test pins the default only by string-matching the script source. That is the exact blind spot that let item 0 (the desktop-paint breakage) sit unnoticed. Should assert_the_harness_deletes_a_scratch_dir_under_a_temp_root be called UNCONDITIONALLY as its own test rather than only as the no-candidate fallback? It is already cheap (rustup and cargo are stubbed on PATH), and it would give the gate teeth on both halves.
  (crates/macos-renderer/tests/typecheck_harness_guard.rs: the converse helper is reached only from the `let Some(victim) = ... else` arm; the_harnesss_default_scratch_dir_stays_under_a_temp_root asserts on source text, not behaviour.)
- Acceptance criterion 1 asks that the harness repair be proven by RUNNING it, not by reading it. The only evidence that landed is prose (spike README plus DECISIONS.md saying it ran clean on 2026-07-31 against aarch64-apple-darwin); no transcript is committed and nothing in CI runs the harness. This repo elsewhere pins recorded runs against their evidence files (see the windows-probe-evidence-files-agree test). Is a prose claim the intended bar here, or should the harness repair get a gate or a committed run record?
  (docs/spikes/macos-wkwebview-renderer-backend/README.md (RUN clean on 2026-07-31) and DECISIONS.md choice 3; work/notes/observations/macos-typecheck-stand-in-core-drifts-unwatched-2026-07-31.md files only the stand-in-core half of the gap.)
- The guard test writes into the REAL home directory ($HOME/.werust-typecheck-harness-guard-probe) on every ordinary gate run, with no env lever to redirect it, which cuts against the work contract's shared-write isolation rule. It is arguably unavoidable (the test needs a path provably outside every temp root) and cleanup is unconditional, so this is a decision to RATIFY rather than a defect. One concrete nit though: unlike the sibling helper, the probe directory name carries no process id, so two concurrent test runs sharing a HOME (two worktrees, parallel gates) can delete each other's victim mid-assertion. Should the name take the same process-id suffix?
  (crates/macos-renderer/tests/typecheck_harness_guard.rs a_probe_dir_outside_every_temp_root uses a fixed name, while assert_the_harness_deletes_a_scratch_dir_under_a_temp_root uses std::process::id() for its stubs and scratch dir.)
- Ratify the item-2 resolution recorded in DECISIONS choice 2: the pull_request filter gained the two spike-docs paths (making the README claim true) and deliberately stays narrower than push, keeping crates/renderer and crates/fetcher push-only, and leaving crates/werust-core on the PR trigger as it already was. The narrowness is now pinned by a test, so widening it later has to change a test plus a comment. This matches the requeue's instruction and the Windows sibling's shape, but the human's open question (should werust-core gate PRs on macos-14 minutes at all?) is explicitly left unanswered.
  (.github/workflows/macos-renderer.yml pull_request block plus its header comment; crates/macos-renderer/tests/macos_backend_shape.rs the_readme_claim_about_when_the_leg_runs_matches_the_pull_request_trigger.)

First, the task minted a NEW spike directory (docs/spikes/macos-spike-doc-accuracy-and-harness-guard/) holding only a DECISIONS.md with no README, where the requeue said to record the decision in the spike DECISIONS block; it is linked from the wkwebview spike README, but it sets a precedent that a docs-tidy task gets its own spike dir.
