# The DPI fix should NOT be expected to close the phantom-scrollbar task: nothing about the page's WIDTH changed (2026-07-31)

Noticed while closing `windows-chrome-must-scale-with-the-display-dpi`, which the sibling task `windows-page-shows-a-phantom-horizontal-scrollbar` asks to be re-checked on top of (its hypothesis 1 is "the same physical-versus-logical pixel mismatch"). The DPI work changes the page window's TOP (`page_top` is now a scaled toolbar height) and its height, and changes nothing horizontal: `chrome.rs::relayout` still places the page at `x = 0` with the shell's full client width, exactly as before, and `crates/windows-renderer/src/backend.rs` still sets the WebView2 controller's bounds from `GetClientRect(container)` on `WM_SIZE` (lines 562, 1125, 1425) — physical client pixels, which is the space `SetBounds` expects from a DPI-aware host. So no logical/physical mixing was found on that path, and none was removed.

Not investigated further (out of scope: that scrollbar is its own task, which asks for the three rects plus the page's own `innerWidth`/`clientWidth`/`scrollWidth` measured with numbers). Recorded so the next agent does not open that task expecting the DPI change to have fixed it, and starts from hypotheses 2 and 3 instead.
