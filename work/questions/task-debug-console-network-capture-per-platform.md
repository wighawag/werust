## Q1

**'task:debug-console-network-capture-per-platform' was bounced — how should we proceed?**

> PR/code review (Gate 2) blocked this work:
> - Desktop: a FAILED resource is recorded TWICE, and the second row claims content-verified for a request that failed. WebKit emits WebResource::failed and then ALSO emits finished (webkitWebResourceFailed ends by calling webkitWebResourceFinished; the GTK docs say so explicitly: in case of errors the failed signal is emitted BEFORE this one). install_debug_capture connects BOTH connect_finished (record(..., finished_ok=true)) and connect_failed (record(..., false)) on the same WebResource, so every failed load pushes two NetworkEntry rows, and for an ipfs:// resource the finished row passes finished_ok=true and therefore gets TrustPosture::ContentVerified. A hash-mismatched / failed ipfs:// subresource is displayed as content-verified in the very surface whose job is trust honesty. This breaks acceptance criterion 2 and 5, DECISIONS.md Decision 4 (one request, one row) and Decision 7 (a failed ipfs:// resolution is honestly unverified-origin). The in-code comment saying a verify failure lands on failed INSTEAD of finished is factually wrong. (crates/webview-renderer/src/backend.rs install_debug_capture: resource.connect_finished(... record(Some(resource), true)) plus resource.connect_failed(... record(Some(resource), false)); WebKit source UIProcess/API/glib/WebKitWebResource.cpp webkitWebResourceFailed calls webkitWebResourceFinished)
> - iOS: the main-document reconciliation never fires on an ENS-named page, which is the exact case it was mandated for. Both scheme handlers compute mainFrame as core.chrome().url == url.absoluteString, but ChromeState.url_text is the DISPLAY identity, not the request URL: on an ENS load the shell pins url_override so url_text is e.g. ronan.eth while the scheme-handler URL is ipfs://<cid>/index.html. So mainFrame is false, the main-document row keeps the plain per-request content-verified posture, and the Network tab shows content-verified while the chrome trust indicator shows name-via-trusted-rpc on the same screen. That contradiction is precisely what the task forward-pointer item 3 and DECISIONS.md Decision 5 exist to prevent. The didFinish path does not compensate: it skips ipfs:/werust: URLs. (crates/werust-ios/App/Sources/WKWebViewShellController.swift IpfsSchemeHandler and WerustSchemeHandler: let mainFrame = core.chrome().url == url.absoluteString; crates/werust-core/src/lib.rs refresh_chrome sets chrome.url_text from url_override (the pinned .eth name) first)
> - DECISIONS.md Decision 5 states that desktop identifies the main document via WebView::main_resource(), falling back to the lifecycle current URL. main_resource is used NOWHERE in the tree (zero hits across crates/); the only mechanism shipped is a raw string compare of the START url against life.current_url(). That compare is fragile in two recorded ways: a redirected main document keeps its pre-redirect URL in ResourceCaptureState while the lifecycle holds the final one, and this repo already recorded that WebKitGTK reports the authority-less ipfs:///<cid> form for the same entry the shell stored as ipfs://<cid> (the reason normalize_ens_page_key exists). When the compare misses, the main row falls back to the per-request posture and can again contradict the indicator. Either wire main_resource / is-main-resource as documented, or correct the decision record to describe what actually landed. (docs/spikes/debug-console-network-capture-per-platform/DECISIONS.md Decision 5 vs crates/webview-renderer/src/backend.rs ResourceCaptureState::record: (life.current_url() == Some(self.url.as_str())).then(|| life.posture()))
