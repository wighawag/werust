## Decisions taken while adding the neutral loading state to the trust indicator

Recorded for reviewer/human ratification (per the durable-decision rule). None are load-bearing/hard-to-reverse; the build proceeded. The done record for `chrome-loading-state-resets-trust-indicator` should link here.

1. **The neutral loading state is a DISPLAY-RULE precedence (`loading` wins over the posture), NOT a new `TrustPosture` variant.** USER-VISIBLE display rule that TOUCHES the trust-indicator display on all three platforms. While `ChromeState::is_loading()` is true the indicator shows the loading badge regardless of `trust_posture`; the real posture appears only once the load settles (finished/failed/idle). Coherence: I deliberately did NOT add a `TrustPosture::Loading` variant, because `TrustPosture` is defined (renderer crate, `docs/adr/0001`/`0006`) as "how did the CURRENT page's bytes load" (an ACTUAL-load-path fact), and "a load is in flight" is a different axis (`LoadState`) the chrome already models. Minting a posture variant would re-mean `TrustPosture` (mixing lifecycle into a load-path fact) and force a wire-name + a matrix cell + a fifth badge everywhere. Instead the precedence sits at the SAME display layer as the existing two-axis loudest-wins rule (`NameViaTrustedRpc` > `MutableName` > `ContentVerified`), reading the `is_loading()`/`loading` fact each platform already has. Alternative considered: reset `trust_posture` to a sentinel during load in core — rejected, it would lose the settling posture and still needs a display branch. Choice sites: `werust::{trust_indicator,trust_indicator_detail,trust_indicator_css_class}` (`crates/werust/src/main.rs`), `Chrome.trustIndicator()` (Kotlin `WerustCore.kt`, Swift `WerustCore.swift`).

2. **The neutral loading label is `"⋯ loading…"` with a grey `trust-loading` CSS class, and makes NO trust claim** (it never contains the word "verified" and never asserts the origin is (un)verified). USER-VISIBLE default text/glyph. It mirrors the existing badge shape (glyph + short label) and reads before colour, and the tooltip says werust "is not yet asserting a trust level for it". The grey `#5c5c5c` is a fourth colour distinct from the green/blue/purple/amber posture badges. Applied identically on mobile so the four platforms show the same neutral badge from the same `loading` fact.

3. **`is_loading()` is `Started || Committed` only — a FAILED load is NOT loading**, so a failed load shows its (unverified) posture, not the spinner (acceptance: "a failed load shows its failure state, not a stale success posture"). This falls out of the existing `LoadState::is_loading()` definition (`renderer` crate); no change was needed, but it is load-bearing for the failed-load AC so it is noted.

4. **The stale name/posture/error clearing was ALREADY correct in core; this task only added the display rule + Rust tests that pin it.** `BrowserShell::navigate` already sets `url_override = None` and `last_error = None`, and the backend's `LoadLifecycle::begin` (and the fake backend's `navigate`) already reset the posture + both trust-axis flags to untrusted on every fresh load. Two new `werust-core` fake-backend two-page tests assert these invariants end to end (a content-verified page -> a differently-trusted page shows neutral loading then the new posture; a failed ENS page -> a fresh navigation drops the pinned `.eth` name AND the surfaced error). No core behaviour changed here.

5. **Fixed an adjacent latent bug: the desktop CSS class-toggle set omitted `trust-mutable-name`.** `Chrome::refresh` loops a fixed list of trust classes to remove the inactive ones and add the active one, but that list previously listed only `trust-verified`/`trust-name-trusted-rpc`/`trust-unverified` — so `trust-mutable-name` was never removed once added, and a transition away from a mutable-name page would leave the purple class stuck. I had to touch this list anyway to add `trust-loading`; leaving `trust-mutable-name` out would be incoherent with my own addition (the set must list every class `trust_indicator_css_class` can return). So the set now lists all five. This is a tiny, self-contained correctness fix at the exact site I was editing, not a scope expansion; noted here for visibility. Choice site: `werust::Chrome::refresh` (`crates/werust/src/main.rs`).

6. **Parity: the mobile display rule is Kotlin/Swift, NOT covered by the Rust `verify` gate.** The `trust-indicator` capability is `implemented` on all three platforms in `docs/platform-capability-matrix.toml`, so the loading state had to land on mobile too (acceptance 4). The Rust-testable half (the `loading` fact reaches the mobile edge over the FFI chrome JSON) is already pinned by the existing `ffi_json` tests; the one-line loading-wins branch in each mobile `trustIndicator()` reads that same fact, exactly as desktop does. The matrix `trust-indicator` row description + comment were updated to state the neutral-loading behaviour so the matrix stays honest. There is no Rust unit test for the Kotlin/Swift branches (no such tests exist in the repo; the mobile display mapping has always lived edge-side), so this parity rests on the shared `loading` fact + the matrix note rather than a gate-enforced mobile assertion.
