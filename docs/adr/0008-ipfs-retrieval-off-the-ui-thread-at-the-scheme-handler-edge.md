# `ipfs://` retrieval runs off the UI thread at the scheme-handler edge, with the shared posture marshalled back on-thread

Context: the desktop `ipfs://` scheme handler (`crates/webview-renderer/src/backend.rs`, `install_ipfs`) used to call `resolve_ipfs_request` SYNCHRONOUSLY inside the WebKitGTK scheme-handler closure, which runs on the single GTK main thread, once per request (the main document AND every sub-resource). A trustless-gateway CAR fetch + per-block verify + DAG reassembly is network I/O measured in seconds, so blocking the one UI thread on it froze the window (a real load showed GNOME's ~10s "application not responding" dialog). The retriever is deliberately synchronous (no async runtime, `docs/adr/0004`), so the concurrency has to live at the edge, not in the retriever. This records where that boundary is and how the shared trust posture is kept race-free across it.

## The decision

1. **The concurrency boundary is at the scheme-handler edge, not in the retriever.** The retriever stays synchronous (`docs/adr/0004` is unchanged). `install_ipfs` moves the blocking call off the GTK main thread and completes the `WebKitURISchemeRequest` when the verified bytes are ready. The mechanism is `gio::spawn_blocking` (run the blocking retrieval on gio's shared I/O thread pool) + `glib::MainContext::spawn_local` (await the result and finish the request back on the GTK loop). Because the event loop keeps turning, sub-resource requests each spawn their own worker and proceed concurrently instead of serializing the loop.

2. **Only a `Send` VALUE crosses the thread boundary; nothing `!Send` and nothing GTK does.** The split lives in `crates/webview-renderer/src/offthread.rs`. `retrieve_off_thread` runs on the worker and returns a `RetrievalOutcome` (a plain `Result<SchemeResponse, RendererError>`); it captures only the `Send + Sync` retriever (shared via `Arc`) and the request URI (a `String`). The `WebKitURISchemeRequest` (a `!Send` GObject) and the `Rc<RefCell<LoadLifecycle>>` (the shared posture, `!Send`) are captured ONLY by the `spawn_local` future, which is `!Send` and runs on the main thread, so they are never touched off it.

3. **The shared load lifecycle / trust posture is mutated ONLY on the main thread.** `complete_ipfs_request` (the completion half, run inside the `spawn_local` future on the GTK loop) is the sole place that touches the shared `LoadLifecycle`: on a verified `Ok` it marks the posture content-verified (the shared `TrustPosture::after_verify` rule then surfaces the honest ENS/mutable variant) and streams the bytes; on ANY `Err` it fails the load and leaves the posture untouched. So the worker thread can never race the UI thread's posture updates. This is the DESKTOP ANALOGUE of the Android thread-safety fix (`SyncSession`, `docs/adr` note / `crates/werust-android`): Android's `shouldInterceptRequest` already runs on a WebView worker thread and is serialized against the UI thread by a `Mutex`; desktop achieves the same "one thread touches the posture" invariant by marshalling the mark back onto the GTK loop instead of locking.

4. **Trust and fail-closed behaviour are UNCHANGED.** The exact same `resolve_ipfs_request` (full per-block verify, DAG walk, budget, path resolution) runs, just off the UI thread. Verification still GATES the load: unverified bytes are never delivered to render, a failure still fails the load with its distinct reason, and the posture is upgraded only by a genuinely verified resolution. Splitting the work across two threads changed WHERE the verify runs and WHERE the posture is marked, not WHETHER either happens.

## Platform scope

- **Desktop (WebKitGTK):** fixed here.
- **Android:** already correct BEFORE this task. Its `shouldInterceptRequest` runs on a WebView worker thread (so the Android UI thread never blocks on retrieval), and the shared `CoreSession` is guarded by the `SyncSession` `Mutex` so the worker resolve and the UI-thread drive are serialized. That fix is the precedent this desktop change mirrors.
- **iOS:** NOT addressed here and out of this task's scope. iOS's `WKURLSchemeHandler` start callback runs `core.resolveIpfs` synchronously on the main thread, so it has the same latent freeze, but moving it off-thread also needs an iOS `SyncSession`-style guard (the iOS FFI documents a "main thread only" invariant with no Mutex). Captured for a follow-on task in `work/notes/observations/ios-ipfs-scheme-handler-blocks-main-thread-2026-07-23.md`.

## Considered options

- **Complete the request from the worker thread directly** (e.g. `MainContext::invoke` from the worker, or calling `request.finish` off-thread). Rejected: `WebKitURISchemeRequest` is `!Send` and must be finished on the GTK thread, and `MainContext::invoke` requires a `Send` closure that could not capture the `!Send` request or the `Rc`-shared lifecycle. `spawn_blocking` + `spawn_local` keeps the `!Send` state on the main thread and moves only a `Send` value across.
- **A single dedicated worker thread + a queue** instead of gio's I/O pool. Rejected as more machinery for the same effect: gio's `spawn_blocking` pool already exists in-process, integrates with the GTK main context, and lets concurrent sub-resource fetches run in parallel without a hand-rolled pool. (The pool may rate-limit, which is acceptable: the transport's own timeout still bounds each fetch, `docs/adr/0004`.)
- **Make the retriever async.** Rejected: it directly contradicts `docs/adr/0004` (sync seam, no async runtime). The boundary belongs at the OS edge, which is exactly where the platform already hands us a thread (the GTK loop) to marshal on.
