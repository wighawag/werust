# Platform-capability parity guard: a `verify`-enforced capability matrix that reds the gate on an untracked cross-platform gap

We guard against "a feature silently shipping on one platform only" with a checked-in capability matrix (`docs/platform-capability-matrix.toml`) validated by a plain workspace `cargo test` (`crates/werust-core/tests/platform_capability_parity.rs`) that rides the existing `verify` gate (`fmt && clippy && build && test`): every cross-cutting capability x {desktop, iOS, Android} cell must be explicitly `implemented`, `stubbed` (with a follow-on task slug that resolves to a real task in `work/tasks/{backlog,ready,done}/`), or `n-a` (with a reason) — and a bare untracked stub, a dangling task link, or an omitted cell reds the gate. This is the durable fix for the class of bug that hid the mobile `ipfs://` gap: `register_scheme_handler` was an empty `{}` no-op on both mobile backends, a whole capability shipped desktop-only, the release looked green, and nothing flagged it.

## Status

accepted

## Considered Options

- **A checked-in capability matrix (chosen, granularity = capability x platform).** One row per user-facing capability, a cell per shipped context. Cheap to keep honest: adding a capability or a platform forces a cell (an omitted cell reds), and a `stubbed` cell that names no real task reds. It catches capability-LEVEL gaps in the language users and specs speak.
- **A no-silent-no-op-seam rule (chosen too, but expressed THROUGH the matrix).** The settled design asked for both. Rather than build a second, separate mechanism (e.g. a proc-macro or a source-scanning test that flags every empty `{}` seam-trait method and demands an inline `// tracked: <slug>` marker), we express the no-op rule as the matrix's `stubbed` state: a no-op'd seam method on a backend is the method-level face of a capability that is `stubbed` on that platform, and the matrix already requires that stub to be marked and task-linked. The current mobile no-ops (`register_scheme_handler` -> `ipfs-render`; `register_script_message_handler` + `inject_script` -> `eip1193-provider`; the default `trust_posture` -> `trust-indicator`) are seeded as tracked `stubbed` cells, and a test pins that they can never be silently flipped to `implemented` while the backend still no-ops them. A separate source-scanning no-op detector was rejected as more brittle (it would fire on every legitimately-empty seam method across the tree — e.g. the native-renderer T0 backend's structural no-ops — producing noise the matrix avoids by speaking at the capability layer).

## Consequences

- **Enforcement point = a plain `cargo test`, no CI change.** The guard lives in `werust-core` (the one shared crate every OS edge sits over, carrying no GTK/SDK deps) so it runs inside the pure-Rust gate, exactly like the sibling `release_plumbing_shape.rs`. A tag push cannot ship a silently-one-platform feature.
- **Granularity is capability x platform, not method x backend.** The matrix is authored in the vocabulary of `CONTEXT.md` (a capability is a cross-cutting user-facing behaviour), which is what a reviewer and a release reader reason about. Method-level no-ops are caught via the capability they belong to.
- **Seeded with current reality (2026-07-23), so the guard is green today ONLY because gaps are tracked.** `ipfs-render`, `eip1193-provider`, and `trust-indicator` are desktop-`implemented`, iOS/Android-`stubbed`. The parity-guard task's original seed listed the latter two as `implemented`-everywhere; against the code that was false (both mobile backends leave the provider bridge and trust posture at seam-default no-ops), so the seed was corrected to reflect reality. See `work/notes/observations/mobile-provider-and-trust-are-also-silent-no-ops-2026-07-23.md`.
- **Known linkage nuance (surfaced, not buried).** All three mobile stubs currently link to `mobile-ipfs-scheme-interception-ios-and-android`, whose body is scoped to `ipfs://` scheme interception specifically and does NOT explicitly cover the provider bridge or trust-posture wiring on mobile. The guard's resolution rule is deliberately mechanical (the slug must name a task file that EXISTS), because "does this task's prose cover this capability" is not machine-checkable. A human may want a dedicated mobile task so each stubbed cell links to a task that genuinely covers ITS completion; until then the gaps are at least tracked, not hidden. Recorded in the observation note above and the task's done record.
