# A Windows desktop build would be WebView2 via `webview2-com`, and it is DEFERRED until the shared desktop-chrome layer exists and the origin question is probed on Windows

A Windows desktop werust is feasible and the shape is now settled: a new `Renderer` backend over Edge **WebView2**, bound with the **`webview2-com`** crate, driven from a plain Win32 window, with no widening of the `Renderer` trait. It is nevertheless **DEFERRED**, because the cost is a fourth full shell (22 to 39 person-days at capability parity), nothing on the conformance ladder is waiting on it, and its one genuinely open question (does a registered `ipfs://` scheme really give a working same-origin `fetch` + `pushState` in the evergreen runtime?) is only decidable on a Windows machine, which this research did not have. What IS decided now, and recommended as the immediate next step, is the one piece that makes Windows AND macOS cheap and is worth doing on its own merits: extracting the desktop chrome PRESENTATION rules out of the GTK shell into the shared toolkit-free core, so a second (or third) desktop window only PAINTS.

## Context

werust ships three OS edges over one Rust core (`docs/platform-capability-matrix.toml`): desktop Linux on GTK4 + WebKitGTK, Android on the System WebView, iOS on WKWebView. Windows has no path at all, because `webkit6` wraps a Linux-only library and WebKitGTK publishes no Windows DLLs. The `Renderer` seam (`crates/renderer/src/lib.rs`) is the place a new engine plugs in, and a backend qualifies only if it satisfies the trust hooks (provider injection + custom-scheme interception), not merely if it renders.

The task that produced this ADR was funded with an explicit instruction to answer more than "can Windows work?": Windows and macOS are both "a new `Renderer` backend over the platform's system webview, driven from a native window", and werust already has a third instance of that shape shipping (iOS). So the ADR must also decide whether there is ONE shared desktop shell worth extracting, because `macos-desktop-build` will be split using that answer.

The load-bearing technical worry was specific and well-earned. On Android an `ipfs://` document served through `WebViewClient.shouldInterceptRequest` gets an OPAQUE origin, so Blink rejects `fetch('ipfs://...')` before the network stack and `history.pushState` throws `SecurityError`: every SvelteKit client-side navigation dies with no signal werust can see. That cost a field bug and the `crates/werust-android/rust/src/origin_map.rs` internal-`https` origin map to fix (`docs/spikes/mobile-ronan-eth-buttons-no-navigation/DIAGNOSIS.md`). WebView2 is the same Blink engine. If it repeated Android's failure, a Windows build would inherit Android's workaround; if it gave real tuple origins, Windows would behave like desktop and iOS.

## Findings

**1. WebView2 has real scheme REGISTRATION, not just interception, and documents tuple origins.** `ICoreWebView2CustomSchemeRegistration` (Win32 SDK 1.0.1587.40) is passed to `ICoreWebView2EnvironmentOptions4::SetCustomSchemeRegistrations` at environment creation. With `HasAuthorityComponent = TRUE`, Microsoft documents that "the URIs with this scheme will be interpreted as having a scheme and host origin similar to an http URI" and that `custom-scheme-with-host://hostname/path` has origin `custom-scheme-with-host://hostname`; with it FALSE the origin is opaque "similar to a data URI". `TreatAsSecure` (effective only with `HasAuthorityComponent`) makes it a secure context. So WebView2 is architecturally CLOSER to WebKitGTK's `register_uri_scheme` than to Android's interception hook. That is the answer to the task's headline question, at the documentation level.

**2. But the specific sub-behaviour werust needs is an open WebView2 bug, and the corner regresses in stable.** werust does not need "a document renders", it needs a same-origin `fetch('/blog/__data.json')` plus `pushState`. [WebView2Feedback #4328](https://github.com/MicrosoftEdge/WebView2Feedback/issues/4328) ("Custom schemes don't work with the js fetch() api") has been OPEN since 2024-01-28, last confirmed 2025-12-12 with `XMLHttpRequest` failing and the `WebResourceRequested` handler never firing. [#4362](https://github.com/MicrosoftEdge/WebView2Feedback/issues/4362) (CSS `url()` subresources 401 without reaching the handler) is open too. [#5495](https://github.com/MicrosoftEdge/WebView2Feedback/issues/5495) is worse for risk than for feasibility: in January 2026, stable runtime 144 broke plain LINK navigation from custom-scheme documents, and Microsoft fixed it in canary within two days. The runtime is EVERGREEN and werust cannot pin it, so this corner can break under users without werust changing a line. Some of #4328 is consistent with reporters omitting `HasAuthorityComponent` (an opaque origin sends `Origin: null`, and the documented rule is that no cross-origin request from an opaque origin is allowed), so the honest verdict is **undetermined**, not broken.

**3. The largest real-world Rust consumer avoids the API and ships werust's Android workaround instead.** Tauri goes through `wry` (0.56.0, ~9.3M recent downloads), and wry does not use custom-scheme registration on Windows: `src/custom_protocol_workaround.rs` maps `{scheme}://host/path` to `http(s)://{scheme}.localhost/path` and filters `WebResourceRequested` on that prefix, with a header comment naming both Windows and Android as needing the same workaround. A GitHub search of `tauri-apps/wry` for `CustomSchemeRegistration` returns zero issues or PRs. Lapce and Zed are irrelevant here (both render their own UI, no system webview). werust's `origin_map.rs` is the same mechanism with a better shape for a browser (the CID is the HOST, so two content-addressed sites are not same-origin; `.invalid` per RFC 2606 can never resolve). **So the fallback, if the probe says the real scheme does not work, is not new work: it is promoting a module werust already owns and unit-tests.**

**4. Bindings: `webview2-com`, not the `webview2` crate, and not `wry`.** `webview2-com` + `webview2-com-sys` (wravery/webview2-rs, MIT) are at 0.39.1 (2026-03-11) with ~6.07M recent downloads, generated from the WebView2 winmd with `windows-rs`, and they are what wry itself depends on. They already expose the whole custom-scheme path in Rust (`CoreWebView2CustomSchemeRegistration::new` / `set_has_authority_component` / `set_treat_as_secure` / `set_allowed_origins`, plus `CoreWebView2EnvironmentOptions::set_scheme_registrations`). The `webview2` crate (sopium) last shipped 2021-10-20 and predates the API: do not use it. `wry` as the whole backend was considered and rejected (see Considered options).

**5. The `Renderer` trait expresses WebView2 with NO widening, and on several rows more natively than the existing edges.** Full method-by-method map in the spike README section 5. Highlights: session history is native (`GoBack` / `get_CanGoBack` / `add_HistoryChanged`); the SPA same-document URL change is native (`add_SourceChanged` with `IsNewDocument == FALSE`, where desktop infers it from `notify::uri`); `ViewHandle`'s opaque pointer carries an `HWND` as-is; a scheme response can carry a real status code (`CreateWebResourceResponse`), so the `_redirects` / site-404 row works; ADR-0008's off-UI-thread rule is satisfiable with `GetDeferral` + `Deferral::Complete`, and the existing `crates/webview-renderer/src/offthread.rs` split (a `Send` outcome computed off-thread, applied on the marshalling thread) is toolkit-free and reusable unchanged; ADR-0009's follow-the-OS rule is a one-liner (`PreferredColorScheme = AUTO`); ADR-0010's new-window-in-place feeds `renderer::new_window_action` from `add_NewWindowRequested` + `put_Handled(TRUE)`; devtools is real Chrome devtools (`OpenDevToolsWindow`); network capture via `WebResourceRequested` on `*` matches desktop's reach, and console capture can use either the shared injected shim or the DevTools protocol. The ONE constraint: the SET of custom scheme NAMES is fixed at environment creation and immutable for the browser-process lifetime, while `register_scheme_handler` is called after construction today. The fix is a lazy environment (eager container `HWND` so `view_handle` works, environment + controller created on first `navigate`), not a trait change.

**6. Runtime and toolchain are not obstacles, but "no installer" is not a promise.** The Evergreen Runtime is part of Windows 11, and "the vast majority of Windows 10 devices have [it] installed already", with Microsoft recommending the app CHECK and deploy the ~2MB bootstrapper otherwise. Windows 7/8.1 are out of scope for everyone (dropped after runtime 109, January 2023). Linking: `*-pc-windows-msvc` statically links `WebView2LoaderStatic.lib` (single-exe zip); `*-pc-windows-gnu` needs `WebView2Loader.dll` shipped alongside. CI: add a native `windows-latest` job rather than cross-compiling from Ubuntu, exactly as ADR-0002 already concluded for the Linux desktop leg (the zigbuild cross path could not link the system webview, so that leg is a native `cargo build`); the pure-Rust `verify` gate on Ubuntu cannot compile a `#[cfg(windows)]` backend, so a Windows task must bring both source-shape tests (the repo's existing pattern) and the platform job, plus the `windows` column in `docs/platform-capability-matrix.toml`.

**7. Cost: a fourth shell, dominated by the chrome, not by the engine.** Measured against the shells this repo has already built (`webview-renderer` 3,404 lines; the GTK shell `main.rs` 2,995; the Android edge 4,073 Rust + 1,980 Kotlin; the iOS edge 3,271 Rust + 1,771 Swift): probe 1-3 days, shared presentation extraction 2-4, the WebView2 `Renderer` backend 8-12, the Win32 window + chrome 8-14, parity column + forced stub tasks 1-2, CI + packaging 2-4. Total **22 to 39 person-days**. The single biggest line is painting the chrome, and macOS pays that same line.

## Decision

**DEFER the Windows desktop build.** Do not fund the Windows shell now. Revisit when ANY of these becomes true: (a) a real user or distribution demand signal for Windows appears; (b) the pure-Rust renderer reaches T1 and the platform surface becomes the growth edge rather than the renderer; (c) macOS lands and the shared desktop-chrome layer has already absorbed the per-platform cost, making Windows a 2-to-3-week job instead of 5-to-8. This is a priority decision, not a technical one: nothing found here is disqualifying.

**Decided now, so it is not re-researched:** if Windows is funded, it is **WebView2 via `webview2-com`**, a `Renderer` backend in the existing `crates/webview-renderer` (or a sibling crate) plus a Win32 window; NOT the native renderer (multi-year, ADR-0001's phase-3 direction), NOT GTK4-on-Windows (no WebKitGTK there; GTK4+WebView2 interop adds MSYS2/vcpkg for nothing), NOT `wry` (see below), and NOT the `webview2` crate.

**Decided now, and recommended as the next task a human can dispatch: extract the desktop chrome PRESENTATION into the shared core.** Today the display rules are triplicated: `crates/werust/src/main.rs` (`status_line`, `trust_indicator`/`_detail`/`_css_class`, `error_banner_*`, `invalid_entry_badge_*`, `load_progress_*`) in Rust for GTK, `WerustCore.kt` (`statusLine()`, `trustIndicator()`, `errorBanner()`, ...) in Kotlin, and `WerustCore.swift` twins in Swift. Each is a pure function of `ChromeState`, so each is core logic living in an edge. Move the Rust copy into the shared toolkit-free core beside `ChromeState`, leave the GTK file as a pure painter, and every later edge (Win32, AppKit, and eventually the mobile twins) paints from ONE derivation. This is a behaviour-preserving refactor whose existing unit tests move with it, it is worth doing with zero new platforms, and it is what turns "a fourth shell" into "a fourth window".

**No new seam concept is introduced.** "Seam" in this codebase means a hot-swappable interface with alternative implementations (`Renderer`, `ScriptEngine`, `Fetcher`). A "desktop shell seam" would duplicate `Renderer` + `BrowserShell` at the wrong layer and re-mean the word. The shareable thing is presentation in the core; the unshareable thing is the window, and each platform stays an OS edge that PAINTS. (Rejected: a `DesktopShell` trait over GTK/Win32/AppKit, which needs a cross-platform GUI toolkit werust has deliberately not adopted; and rendering werust's own chrome in a second webview, which is a much larger, ADR-0001-adjacent decision.)

**The origin mechanism stays OPEN, gated on a probe.** (ANSWERED 2026-07-30 by the probe this paragraph specifies: the registered scheme WORKS — see [Amendment 2](#amendment-2-2026-07-30--gate-0-answered-windows-serves-real-ipfs-origins).) Gate 0 of any Windows work is a Windows-only probe, the analogue of the committed Android probe `SpaClientNavOriginTest.kt`, designed in the spike README section 4: canned bytes, no core, no IPFS, two cases (real registered `ipfs://` with `HasAuthorityComponent` + `TreatAsSecure`, versus the internal `https://<cid>.ipfs.werust.invalid` origin), asserting for each the document origin string, whether a same-origin `fetch` resolves AND fires `WebResourceRequested`, and whether `pushState` throws. Case A passing means Windows serves real `ipfs://` origins like desktop and iOS. Case A failing means `origin_map.rs` is promoted from an Android module to a shared one and the Windows edge maps URLs exactly as Android does. The probe must be re-runnable, because the runtime is evergreen and this corner has demonstrably regressed in stable. This repo has already paid once for settling a platform-origin question from documents instead of a device; not repeating that is the whole point of putting the probe first.

**How `macos-desktop-build` should be split** (the forward-pointer's question, answered against the precedent rather than from first principles): **one shared chrome-presentation layer, separate per-platform window/webview edges.** The precedent already in the repo is exactly this: the iOS edge drives WKWebView through the shared Rust core, and what it shares is the LOGIC (`BrowserShell`, `ChromeState`, the trust rules) while its window and controls are wholly platform-specific and its presentation rules are, regrettably, re-derived in Swift. So the generic part is real but it is the core, not the shell. Cut `macos-desktop-build` into: (1) **the shared desktop-chrome presentation extraction** (platform-neutral, no macOS content, do it FIRST because it serves Windows, macOS and eventually the mobile twins); (2) **the WKWebView + AppKit backend and window** (leaning on `IosBackend`/`CoreSession`, which is already a working WKWebView `Renderer` backend); (3) **the `macos` parity-matrix column plus the stub tasks the guard then forces** (21 capability rows today, each needing `implemented` / `stubbed` with a real task / `n-a` with a reason); (4) **the CI packaging leg** on the existing `macos-14` runner (lipo, `.app`, unsigned zip). Sub-task 1 is shared with any future Windows work and should not be re-cut per platform. Linux/GTK stays a fourth, differently-shaped edge: it also becomes a pure painter after sub-task 1, but its widgets share nothing with Win32 or AppKit, so "generic" here means generic ACROSS THE PRESENTATION, not across the toolkits.

**And if only one new desktop platform is ever funded, do macOS first.** Its origin question is much better placed (WebKit gives `WKURLSchemeHandler`-served documents real tuple origins and the iOS shell ships on that mechanism, though note the repo's own honesty caveat: iOS parity there is a recorded MECHANISM ANALYSIS whose runtime confirmation still awaits a Mac, `mobile-ronan-eth-buttons-no-navigation` DIAGNOSIS.md, "iOS parity"), it reuses an existing working backend (`IosBackend`), and its CI runner already exists. Windows carries the one genuinely unproven behaviour and a brand-new runner.

## Considered options

- **WebView2 via `webview2-com` (chosen shape, deferred timing).** Full control of every hook werust's capability rows need, mature and heavily exercised bindings, single-exe artifact on msvc.
- **`wry` as the Windows backend (rejected).** It would supply less code and, as of 0.56, even exposes session history. But it gives no per-resource network observation (the `debug-capture-console-and-network` row's desktop reach) and it FORCES the internal-`localhost` origin mapping, taking away the choice the probe exists to make; it also adds `wry` plus a window crate to the trust-carrying path, and werust's `Renderer` trait already is the abstraction wry would provide. Its `custom_protocol_workaround.rs` remains this ADR's most valuable evidence, though.
- **The `webview2` crate (rejected).** Last released 2021-10-20, predates the custom-scheme API, ~3.6k recent downloads.
- **GTK4-on-Windows with an embedded WebView2 (rejected).** No WebKitGTK on Windows, so the engine would be WebView2 anyway; GTK4+WebView2 interop is undocumented and drags MSYS2/vcpkg into the distribution story for no gain.
- **The native Rust renderer on Windows (rejected for Phase 1).** It is the phase-3 direction and nowhere near T1; a Windows build on it is a multi-year project, and it is orthogonal to this decision (when it qualifies, it plugs into the same seam on every OS).
- **`SetVirtualHostNameToFolderMapping` (rejected).** Microsoft documents that `WebResourceRequested` is NOT fired for virtual-host-mapped URLs, and werust serves bytes from a verified DAG, not a folder.

## Consequences

- ~~Windows stays unsupported~~ (overturned by Amendment 1: Windows is funded). `docs/platform-capability-matrix.toml` gains no `windows` column FROM THIS RESEARCH; adding the column remains part of the Windows shell work, not of this ADR.
- The next desktop-shell task in this repo, whichever platform it serves, should start with the shared chrome-presentation extraction. If a second desktop shell lands BEFORE that extraction, the display rules become quadruplicated and the debt compounds in four places.
- The Windows origin answer is deliberately left open. Anyone tempted to close it from documents should read `docs/spikes/mobile-ronan-eth-buttons-no-navigation/DIAGNOSIS.md` first; the probe is cheap and the field bug was not.
- werust's `origin_map.rs` is now known to be the same mechanism Tauri ships on Windows and Android. It should be treated as a candidate SHARED module (not an Android wart) the moment a second platform needs it, and its doc comment's framing as an Android-specific hack will then need updating. (Windows turned out NOT to need it — Amendment 2 — so this remains hypothetical.)
- A user-visible Windows behaviour is pre-specified for whoever builds it: a machine without the WebView2 Runtime must fail HONESTLY (name the missing runtime, point at the download) rather than crash, in the same fail-closed spirit as the rest of the product.

## Amendment 1 (2026-07-30) — the DEFER is overturned: Windows and macOS are funded now

**What changed:** nothing technical. The human read this ADR and funded both new desktop platforms anyway, for REACH: werust is meant to be a general-purpose browser, and a browser that runs only on Linux desktop plus two mobile OSes cannot be evaluated by most of the people it is for. Having the platforms early is also expected to GUIDE the architecture rather than merely follow it.

This is revisit trigger **(a)** of the Decision block firing ("a real user or distribution demand signal for Windows appears"), not a technical reversal. Every finding above stands, including the parts that make the DEFER look attractive: the cost is still a fourth (and fifth) shell dominated by chrome painting, and the Windows origin behaviour is still UNDETERMINED.

**What the funding does NOT change:**

- **The probe is still gate 0 for Windows.** No Windows shell code is written before the origin probe answers whether a registered `ipfs://` scheme really gives a working same-origin `fetch` + `pushState`. The probe runs on a `windows-latest` CI runner, so it needs no Windows hardware; that is the whole reason it can go first. If it fails, the mechanism is the promoted `origin_map.rs`, and that is a decision the probe makes, not a preference.
- **The shared chrome-presentation extraction still goes first, and matters MORE now.** With two new windows funded, the Consequences bullet above ("if a second desktop shell lands BEFORE that extraction, the display rules become quadruplicated") is no longer hypothetical: it would become quintuplicated, since the Kotlin and Swift twins already exist.
- **macOS still leads Windows** among the two shells, for the reasons in the Decision block: a better-placed origin story, an existing `macos-14` runner, and an existing working WKWebView backend to lean on.
- **The sizing stands.** 22 to 39 person-days for Windows, less the shared extraction; macOS is comparable minus its engine work. Funding does not shrink the chrome-painting line, it only decides to pay it.

**The verification constraint, recorded honestly:** neither shell can be verified on real hardware from this development machine (no Mac, no Windows box). Both must be built blind and verified in CI, exactly as the iOS shell was, and that path has a known cost: this repo already carries a recorded MECHANISM ANALYSIS for iOS origins whose runtime confirmation still awaits a Mac (`docs/spikes/mobile-ronan-eth-buttons-no-navigation/DIAGNOSIS.md`). Each new platform should therefore land with an explicit statement of what was proven by CI versus what remains analysis awaiting hardware, rather than letting the distinction blur.

**Order funded:** (1) shared chrome-presentation extraction, (2) the Windows origin probe on CI, (3) the macOS WKWebView backend + window, (4) the Windows shell built on the probe's verdict, (5) parity columns and packaging legs for both.

## Amendment 2 (2026-07-30) — gate 0 answered: Windows serves REAL `ipfs://` origins

**What changed:** the one open question in this ADR is now MEASURED, not undetermined. Task `windows-ipfs-origin-probe-on-ci` built the probe this ADR specified (`crates/windows-origin-probe`, run by `.github/workflows/windows-origin-probe.yml`) and ran it on a `windows-latest` runner. Full verdict, evidence and re-run instructions: [`docs/spikes/windows-ipfs-origin-probe-on-ci/README.md`](../spikes/windows-ipfs-origin-probe-on-ci/README.md); judgement calls: [`DECISIONS.md`](../spikes/windows-ipfs-origin-probe-on-ci/DECISIONS.md).

**The answer: the registered scheme.** On WebView2 Runtime **150.0.4078.65**, an `ipfs://` scheme registered through `ICoreWebView2CustomSchemeRegistration` with `HasAuthorityComponent = TRUE` + `TreatAsSecure = TRUE` gives the document the real tuple origin `ipfs://<cid>`, a secure context, a same-origin `fetch` that RESOLVES *and* fires `WebResourceRequested`, and a `pushState` that succeeds. A SvelteKit-shaped client-side navigation therefore works. The internal-`https` origin (case B) also works, but is not needed.

So, per this ADR's own decision rule: **the Windows shell serves real `ipfs://` origins, like desktop Linux and iOS. `origin_map.rs` is NOT promoted; it stays an Android module**, and Android remains the only mapped platform. The Consequences bullet below about `origin_map.rs` becoming a shared module does not fire.

**Why it is believable:** the same run carries a NEGATIVE CONTROL — the identical URL and bytes with `HasAuthorityComponent = false` — which reproduced the Android failure verbatim, Blink's `URL scheme "ipfs" is not supported` message included, with the handler never firing and `pushState` throwing `SecurityError`. The probe can fail; it did not.

**What this does NOT change:** the runtime is still evergreen and this corner still regressed in stable 144 (#5495). The probe therefore ASSERTS against a recorded `expected.json` and goes red naming the field that moved, and the fallback mechanism (case B) is now known to work on WebView2 too — so a future regression is a re-decision, not a dead end. Everything else in the breakdown (lazy environment creation for the scheme-name-set constraint, the shared chrome-presentation extraction going first, macOS leading Windows) stands unchanged.

## Amendment 3 (2026-07-30) — the WebKit half is measured too, and Amendment 1's iOS caveat is settled at the mechanism level

**What changed:** Amendment 1 recorded, as the honesty cost of building blind, that this repo carries a MECHANISM ANALYSIS for iOS origins whose runtime confirmation still awaited a Mac. It no longer does. Task `macos-wkwebview-renderer-backend` built `crates/macos-origin-probe`, the WebKit analogue of the Windows probe this ADR specified, and ran it on the existing `macos-14` runner: [run 30563185521](https://github.com/wighawag/werust/actions/runs/30563185521), macOS 14.8.7 (Build 23J520), AppleWebKit/605.1.15. Verdict, evidence and the honest CI-versus-hardware split: [`docs/spikes/macos-wkwebview-renderer-backend/README.md`](../spikes/macos-wkwebview-renderer-backend/README.md); judgement calls: [`DECISIONS.md`](../spikes/macos-wkwebview-renderer-backend/DECISIONS.md).

**The answer, the same as on WebView2: the registered scheme.** A `WKURLSchemeHandler`-served document gets the real tuple origin `ipfs://<cid>`, a same-origin `fetch` that RESOLVES *and* fires the handler, and a `pushState` that succeeds. The negative control (the identical bytes with no handler-served origin, the handler still installed) reproduced the Android failure shape in the same run, so the probe can fail and did not. `origin_map.rs` stays an Android module on this platform too.

**Why it settles iOS as well as macOS:** `WKURLSchemeHandler` is ONE WebKit class, and macOS and iOS are two ports of that engine. What the run measured is a property of the port, not of AppKit. The device-level residual risk stays open and named (something iOS-specific in the shell's own wiring, not in WebKit's origin model); the load-bearing half of the caveat is measured.

**What it did NOT settle:** it is a CI runner, not Mac hardware in front of a human, so nothing about rendering, input, focus, HiDPI or the responder chain is verified by it. Amendment 1's requirement that each new platform land with an explicit CI-versus-hardware statement is met by that spike README, not retired.

**One prediction moved:** case A's `isSecureContext` was predicted FALSE and measured TRUE (WebKit grants a handler-served origin a secure context with no `TreatAsSecure` equivalent needed). It decides no mechanism, and the recorded verdict was re-stamped WITH that reason rather than silently overwritten, which is the contract both probes hold themselves to.
