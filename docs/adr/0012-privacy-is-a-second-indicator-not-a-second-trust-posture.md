# Privacy is a SECOND indicator beside trust, not another trust posture, and it claims network observability only

Context: the chrome's trust indicator answers "could anyone have lied to me about this page?" (`docs/adr/0006`: resolution-trust × mutability, both axes of INTEGRITY). Designing a real icon for it surfaced a second question users actually have, "who can see what I am reading?", and an attempt to fold it into the same badge collapses immediately on the most common case werust has: a direct `ipfs://<cid>` load fetched through a public trustless gateway is **perfectly integrity-verified** (the bytes hash-check; the gateway physically cannot lie about content) and **completely unprivate** (that gateway observes every page you fetch). One badge, one colour, two opposite truths.

The clinching example is external and real: **sprl.it** resolves ENS names using homomorphic encryption so that the server cannot learn which name you asked for, but it can still return a WRONG answer you cannot detect. That is privacy WITHOUT integrity, the exact mirror of the gateway case. No single scale can order these two systems against each other, because they are not on the same scale.

## The decision

**The chrome carries TWO indicators.**

1. **Trust** keeps the model `docs/adr/0006` already defines, unchanged. Nothing in this ADR alters `TrustPosture`, its precedence, or its vocabulary.
2. **Privacy** is a NEW, orthogonal indicator answering "can what I fetch be observed and linked to me?".

**Privacy has a different SHAPE from trust, and this is the load-bearing part.** A trust posture SETTLES once the load finishes and describes the page. A privacy posture is the **worst of every channel the page touched**, and it therefore degrades DURING a load and resets on navigation: an `ipfs://` page begins at whatever the retrieval egress offers, drops when a subresource reaches an Ethereum node, drops again on a third-party font. Implementing it as a settled value would report the FIRST channel rather than the WORST one, which is the failure mode this paragraph exists to prevent.

**The ladder is per-channel, and roughly:** no egress at all (a locally pinned or cached page) > local node over Tor > local node (leaks your IP, and what your node fetches reveals what you read) > public gateway/RPC over Tor (the operator learns the query but cannot link it to you) > public gateway/RPC (the operator learns both). PIR-style resolution (sprl.it's technique) sits high on THIS axis while sitting low on the trust axis.

**The privacy indicator claims NETWORK OBSERVABILITY ONLY. It does not claim unlinkability.** This boundary is part of the decision, not an implementation note. Tor Browser's entire premise is that transport anonymity is insufficient because fingerprinting re-identifies you anyway, so a green privacy badge awarded for "you are on Tor", in a browser whose renderer is trivially fingerprintable, would be a lie of exactly the kind this project refuses everywhere else. Fingerprinting resistance is separate work (`work/specs/proposed/fingerprinting-resistance-tor-browser-grade.md`); until it exists the privacy indicator must not imply it.

**Protocol identity is NOT a third indicator.** Which naming and retrieval system produced this page (IPFS, ENS, IPNS, Swarm, plain https) is delegated to the DETAILS PANEL that either indicator opens, in the same spirit as a browser's certificate details. That panel is the EXISTING trust popover expanded (it already holds the posture explanation, the mutable-name comparison and the bless action), never a second surface.

## Consequences

- **No page werust can load today can be green on privacy**, because every `ipfs://` fetch goes through a third-party gateway and every ENS name through a trusted RPC. Green is deliberately RESERVED: it is unlocked by built-in verified retrieval (Phase-2, `trustless-ens-to-ipfs-phase2-3-helios-and-hardening`), by a light client for names, or by routing (`privacy-routing-socks5h-tor-vpn-and-profiles`). An aspiration nobody can reach yet is honest; a green badge awarded early would not be.
- **Almost the entire ordinary web is privacy-red, permanently**, since every `https://` site is fully observable by its server and your ISP. That is true but risks the badge becoming unread, which is why browsers eventually REMOVED the positive https padlock and now surface only the negative case. Whether the privacy indicator is always visible or appears only when better than baseline or when it DEGRADES is a display decision left open here.
- **Helios changes the mixed-trust question into a privacy question.** Today werust's own injected EIP-1193 provider reaches a trusted RPC from inside a verified page, doing exactly what a page's hardcoded Ethereum node would do. With a light client the provider preserves INTEGRITY, so the built-in provider and a page's own endpoint stop differing on trust and differ only on privacy, which is the axis this ADR adds. A consent model for page-originated egress (`work/notes/ideas/`) can therefore be reasoned about on one axis instead of two.
- **werust is a better host for PIR-style resolution than a website is.** sprl.it documents its own unavoidable weakness: it serves the cryptography as a web page, so it could serve malicious code instead. A native client implementing the same scheme has no such hole, which makes this technique more attractive here than its browser-delivered form suggests.
- **Certificate details for plain `https://` are a per-edge capability, not a uniform feature** (WebKitGTK, WKWebView `serverTrust`, Android `SslCertificate`, WebView2 each expose different information), so the panel's https half needs a parity-matrix row (`docs/adr/0005`) rather than an assumption.
- **Two badges plus a panel costs mobile toolbar width**, which is the same scarce resource that justifies removing back/forward from the mobile edges. A combined mobile affordance opening the same panel is the likely resolution.
