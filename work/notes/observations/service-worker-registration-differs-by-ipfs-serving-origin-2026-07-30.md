# A site's service worker can register on Android's internal-`https` `ipfs://` origin but not on a real custom-scheme origin, so the same site behaves differently per platform (2026-07-30)

Spotted while researching WebView2 for `windows-platform-research`: engines refuse `navigator.serviceWorker.register()` on custom-scheme origins (Tauri closed [tauri#13031](https://github.com/tauri-apps/tauri/issues/13031) with "there's nothing we can do here" for `tauri://` on WKWebView, and Chromium restricts service workers to http/https), while Android's internal-`https://<cid>.ipfs.werust.invalid` origin is an ordinary secure http origin where they DO register (the `ronan.eth` service-worker update check is visible in the Android Network-tab noise recorded in `work/notes/observations/debug-view-network-tab-buried-by-per-nav-favicon-noise-2026-07-28.md`). So an `ipfs://` site with a service worker gets a different execution model on Android than on desktop/iOS, unverified on werust itself and covered by no row in `docs/platform-capability-matrix.toml`.
