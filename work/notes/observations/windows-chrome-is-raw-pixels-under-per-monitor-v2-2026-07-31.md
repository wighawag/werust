# The Win32 chrome lays out in RAW pixels, and the DPI manifest just made that visible (2026-07-31)

Task `windows-release-packaging-leg` embedded `<dpiAwareness>PerMonitorV2</dpiAwareness>` in `crates/werust-windows/app.manifest`, so werust is no longer bitmap-scaled by Windows on a HiDPI display. But every rectangle in `crates/werust-windows/src/chrome.rs` is still a raw-pixel constant (`TOOLBAR_HEIGHT: i32 = 40`, `TRUST_WIDTH: i32 = 210`, …) and `win32.rs`'s `ui_font()` hardcodes a `-15` height, i.e. 96-DPI metrics. `relayout()` never reads `GetDpiForWindow`, and there is no `WM_DPICHANGED` handler.

So on a 200% display the chrome should now draw **crisp but at half its intended apparent size** where it previously drew **blurry but correctly proportioned**. The PAGE is the half that unambiguously improves: WebView2 in a DPI-aware host renders at the real device scale. Nobody has seen either: this is inference from the code plus the manifest, not a measurement, and confirming it is manual step 10 of `docs/spikes/windows-win32-window-and-chrome/README.md` (which already anticipated "the DPI follow-on").

The fix is mechanical but is NOT packaging work, which is why this task did not do it: scale the layout constants and the font height by `GetDpiForWindow(window) / 96` (ideally through a host-independent metrics function the Ubuntu gate can unit-test, the way `profile.rs` is testable), handle `WM_DPICHANGED` by moving to the suggested rect and re-laying out, and do the same for the debug view's own window. The macOS window does not have this problem (AppKit lays out in points).
