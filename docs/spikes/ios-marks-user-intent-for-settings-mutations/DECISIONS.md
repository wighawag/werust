# The iOS intent signal: the decisions this task baked in

Task `ios-marks-user-intent-for-settings-mutations`, spec `settings-mutations-require-user-intent`. The RULE is `docs/adr/0013` and the decisions it baked in are `docs/spikes/settings-mutation-requires-marked-user-intent-in-core-and-on-gtk/DECISIONS.md`; the ANDROID edge's own calls are `docs/spikes/android-marks-user-intent-for-settings-mutations/DECISIONS.md`. This file records only what the iOS edge had to decide on top of them. Its remaining siblings (`macos-`, `windows-marks-user-intent-for-settings-mutations`) face the same questions in their own platform's vocabulary, and macOS faces them in the SAME vocabulary (WebKit's), so they are recorded rather than buried.

## 1. Swift hands WebKit's `navigationType` across the FFI as its RAW VALUE, untranslated

**Chosen:** the Swift hook passes `navigationAction.navigationType.rawValue` (an `Int`, narrowed to `int32_t` by the binding), and the Rust edge names those values (`WK_NAVIGATION_TYPE_LINK_ACTIVATED = 0`, `…FORM_SUBMITTED = 1`, `…BACK_FORWARD = 2`, `…RELOAD = 3`, `…FORM_RESUBMITTED = 4`, `…OTHER = -1`) and decides which of them count as "the user activated this in the page".

**Why:** the navigation KIND is the iOS spelling of the fact the GTK edge marks on (`LinkClicked` / `FormSubmitted` versus `Other` for a script's `location = …`), so it has to reach the rule. The alternative shapes all move a piece of the rule into the layer this project's Linux gate cannot execute and no human here can exercise (nobody on this project has a Mac, `work/notes/findings/apple-signing-tiers-and-the-no-mac-evidence-gap-2026-08-01.md`). Passing the raw value keeps Swift a reporter of facts, and it keeps the whole truth table testable: `every_fact_the_mark_requires_is_load_bearing` names each refused kind by constant.

**The coupling this takes, named:** the numbers are WebKit's, from the public `NS_ENUM(NSInteger) WKNavigationType` in `WKNavigationDelegate.h`, and this repo pins them in Rust where no compiler checks them against the SDK. They are ObjC ABI, so renumbering them would break every app that stores or switches on them; and if WebKit ever did, or added a kind, the failure direction is CLOSED (the rule matches two values and refuses everything else, so a shifted value withholds the mark and the settings form stops applying, legibly, with the page saying `Not changed: …`), never open. The one shape that could fail OPEN is a renumber that moved `.other` onto 0 or 1, which would require WebKit to renumber the two kinds this rule names as well.

**Alternatives considered:** (a) Swift computes `activatedInThePage = (type == .linkActivated || type == .formSubmitted)` and passes a bool: one line of the RULE in the unexecutable layer, and the exact species of hand-written twin `docs/adr/0011` deleted from this edge; (b) Swift translates the enum to a stable STRING and Rust matches on that: no magic numbers, but it is a Swift `switch` (a translation table nothing here can test) traded for a constant table Rust owns, and it invents a second vocabulary for a fact WebKit already numbers; (c) generate the constants from the SDK header, and there is no iOS SDK in the gate to generate from.

**Touches:** `macos-marks-user-intent-for-settings-mutations` (same `WKNavigationAction`, same question: it should either reuse this shape or say why not), and the C-ABI header `crates/werust-ios/Sources/werust_mobile.h`, which documents the mapping for the Swift side.

## 2. iOS needs NO redirect exclusion, because the document fact is read from the navigation's own SOURCE FRAME

**Chosen:** the mark requires main-frame + an activation kind + a `werust://` source document, and NOTHING about redirects. `WKNavigationAction` exposes no redirect flag, and none is synthesised.

**Why the sibling edges have one and this one does not:** GTK reads "the document this navigation starts from" off the LIVE view (`self.view.uri()`), and Android off `WebView.getUrl()`. Both are view state that has already begun moving toward the destination while a redirect re-fires the policy callback, which is the one window in which that check could read the DESTINATION instead of the SOURCE. iOS does not read view state at all: `navigationAction.sourceFrame.request.url` is a property of the navigation being decided, so the fact does not move with a redirect. Excluding redirects would therefore exclude nothing this edge is exposed to, at the cost of a fact iOS cannot report (and an "unknown reads as a redirect" rule would refuse werust's own settings form outright).

**The residual risk, named, and why it is bounded:** if WebKit were to report the PROVISIONAL destination as the source frame's request during a policy decision, an attacker's page could satisfy the document check by navigating to `werust://settings?…` from a link the user tapped. Two things bound it. First, that is not what a frame's request means: an origin/request changes at COMMIT, and the source frame of a navigation is the frame that asked for it. Second, the core's other half is independent of anything this edge reports: `take_mark_for` also requires the request to be the MAIN FRAME by the redirect sink's reckoning, and while a hostile page is still the committed document that sink holds the hostile URL, so the scheme task for `werust://settings?…` is not its main frame and the mutation is refused anyway. This is defence in depth, not a second gate: it is stated here so a later reader knows what carries the weight.

**If a Simulator run ever shows werust's OWN settings form refused,** read `sourceFrame.request.url` in that run before changing the rule: the likely cause is that fact being empty (an about:blank-ish frame), not the rule. The fix is then to take the document from the frame's `securityOrigin` (`protocol`/`host`), which is a COMMITTED-document fact, rather than to weaken the check. Do not paper over it by dropping the document requirement: it is the fact a page cannot forge, and the whole authorisation rests on it.

**Alternatives considered:** (a) require `sourceFrame.securityOrigin.protocol == "werust"` as a SECOND document fact: strictly stronger, but it is an unverifiable requirement on an edge with no runtime evidence at all, so a wrong reading of it would silently kill the settings form on the only edge where nobody would notice; (b) treat "no redirect fact" as unknown and refuse (the Android API 21–23 posture), which refuses every settings-form submission on iOS, i.e. it lands the task without the behaviour it exists for.

## 3. The report is UNCONDITIONAL, and it comes FIRST in `decidePolicyFor`

**Chosen:** `core.notePageNavigation(…)` is the first statement of the navigation-policy hook, before the existing `.backForward` branch, with no condition of its own.

**Why:** this hook already branches (it reports an edge-swipe history move only for a main-frame `.backForward` navigation), so "the Swift layer decides nothing" cannot be asserted as "this body contains no `if`", the way the Android guard asserts it. Making the report the first, unconditional statement gives the guard something exact to pin: no `if` / `guard` / `switch` / `?` / `&&` / `||` may appear before it (`the_ios_swift_shell_reports_the_facts_and_decides_nothing`). Marking is harmless for the navigations that are not settings changes, since the core matches a mark against the exact URL including its query, so there is nothing to gain by filtering first.

**Alternative considered:** report inside a small `if` that skips non-`werust://` targets (fewer FFI calls). It is the same rule fragment in the same unexecutable layer, for a call that is a pointer hand-off on a user-scale event.

## 4. The edge type is `IntentMarker`, the same name the Android edge gave it

**Chosen:** a small iOS-crate type holding the `NavigationIntent` and the `RedirectSink` together, named `IntentMarker`, with the same `note_page_navigation` verb.

**Why:** it is the same concept at the same layer in a second edge crate, so giving it a second name would make the vocabulary say two things about one idea. "Intent" in this codebase already means chrome-marked navigation intent and nothing else (`CONTEXT.md`, `werust_core::intent`), and "mark" is that module's own verb. The two crates cannot SHARE the type (it is a per-edge convenience over the core carrier, and `werust-core` deliberately holds no edge types), so identical naming is what keeps the four edges legible side by side, and it is what will make the fan-in reading of this row cheap.

**What iOS does NOT copy from Android:** the ANR argument (holding the marker beside a session lock). The iOS session has no lock: Swift drives one `CoreSession` from the main thread. The marker still lives on the session and is reached through it, which is the simplest shape here.
