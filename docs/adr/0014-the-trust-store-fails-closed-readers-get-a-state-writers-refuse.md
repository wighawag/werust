# The trust store fails closed asymmetrically: readers get a STATE, writers REFUSE

The trusted-name pin store (`werust_core::pins`, `pins.json`) records what the user personally verified, so "werust cannot read it" must never be read as "the user has trusted nothing". It used to be: `load_from` returned the default (empty) store for any read or parse failure, the parse dropped an entry with no cid, no timestamp or a posture spelling this build did not know, and it de-duplicated two entries for one key by keeping the first. The next save then persisted the survivors, so a single transient failure destroyed every record permanently. While the store is only advisory that costs a missing warning; the moment something READS it to decide what loads (spec `withhold-changed-content-until-trusted`) it becomes a silent browser-wide re-trust, which is why this is settled BEFORE anything depends on the file.

So the store has a THIRD state beside "no records" and "these records", and the two sides of it get DIFFERENT rules, deliberately:

- **Readers get the state.** A read yields either the store or `UndeterminableTrust`, carrying WHY (an unreadable file, a document that is not this wire form, an entry werust cannot read honestly, two entries for one name). A MISSING file is still an EMPTY store: a fresh install is not an error and behaves exactly as it always has.
- **Writers REFUSE while it holds.** `TrustedNamePins::save_to` re-reads the document it is about to replace and returns `false` without touching a byte when that read is undeterminable. This is the half a naive fix forgets and the exploitable one: inserting into what merely LOOKS like an empty store is the same destruction from the write side, one transient failure replacing every record with a single fresh one.

The asymmetry is the point, and it is why this is written down: a reader that merely NOTICES the state is useless if the writer overwrites the file anyway, and a writer that refuses is useless if the reader has already told the chrome the name is unblessed. The refusal lives in `save_to` rather than at each caller so no writer (today's `bless_current_name`, tomorrow's "forget this pin") can forget it, and it is reported as the `false` that already means "the bless holds for this session but could not be recorded" rather than as a new error class.

Neither half may fail a LOAD or make the chrome say LESS. The store is advisory: a file werust cannot read is not a reason to break browsing, so the load is untouched, the posture badge is untouched, and a change warning already derived from what was read still stands. What the chrome does instead is STATE it (`trust_pin_detail`, from the `ChromeState::trust_undeterminable` axis) and offer NO bless (`ChromeState::can_bless_name`), because an offer werust would refuse is worse than no offer, and offering it would itself assert the name is unblessed, which is the one thing werust does not know in that state.

Refined by `trust-store-writes-atomically-and-keeps-fields-it-does-not-know` (the sibling task on the write, `docs/spikes/trust-store-writes-atomically-and-keeps-fields-it-does-not-know/DECISIONS.md`): the refusal is still not an error class and still never fails a load, but it is no longer reported as a bare `false`. `save_to` and `bless_current_name` return a `PinSaveOutcome`, in which `Refused` (this ADR's policy refusal, carrying the same `UndeterminableTrust`) is distinguishable from `CouldNotPersist` (a full disk, no settings directory) and from `NothingToRecord`, because a store that silently failed to persist must not be indistinguishable from one that worked. The same task also removed the mechanism this ADR's write half feared most: the write is now temp-file-plus-rename, so an interrupted save leaves the previous document rather than a truncated one that would refuse every later write.

Consequences worth calling out: this INVERTS the previous promise (the module's fail-safe paragraph and `a_missing_or_corrupt_store_degrades_to_no_pins_never_to_a_broken_load`, rewritten in the same change); a store written by a LATER werust that knows a fifth `TrustPosture` reads as undeterminable in an older build rather than being silently stripped, which is the correct direction but means the older build records nothing until the sibling task on preserving unknown fields lands; and a corrupt `pins.json` now suppresses the bless affordance browser-wide until the file is fixed, which is deliberate, because the alternative is a button whose write is refused.

The secondary shape decisions (why the state is a `ChromeState` axis rather than a variant of `MutableNameTrust`, why the shell KEEPS its cache while the state holds, and why no new chrome-JSON key was minted) are recorded at `docs/spikes/trust-store-fails-closed-instead-of-reading-as-nothing-trusted/DECISIONS.md`.
