# Decisions — clearer-loading-and-error-indicator

Date: 2026-07-23

Durable record of the UX + coherence decisions taken while adding the live loading-progress step and the transient-vs-hard error distinction. None are load-bearing/hard-to-reverse, so the build proceeded; they are recorded here (and linked from the done record) for reviewer/human ratify-or-reverse per the durable-decision rule. Each says what was chosen, why, the alternative(s) considered, and what it touches (which other flag/command/task).

## Context (the field finding this answers)

`work/notes/observations/field-test-v0.2.2-ipns-slow-partial-and-debug-window-2026-07-23.md`, issue C: the loading state is a neutral badge (too weak for a slow/partial load, reads as frozen), and a transient timeout (issue A, `transport error: timeout: global`, retryable — a reload worked) is surfaced identically to a hard fail. This task makes the remaining slow/timeout loads legible.

## Decision 1 — loading PROGRESS is a new `LoadStep` axis on `ChromeState`, NOT a new `LoadState` variant or a new `TrustPosture` variant

USER-VISIBLE loading detail on all four platforms. `ChromeState` gains `load_step: LoadStep` with variants `Idle / ResolvingName / FetchingRecord / FetchingContent / Rendering`, driven by the REAL pipeline (`ens::resolve` -> `ipns::resolve_ipns_name` -> feed CID into the `ipfs://` path -> the backend's `Started`/`Committed`/`Finished` lifecycle). The chrome shows the step as a hint WHILE `is_loading()`, so a slow load reads as "working: fetching content" not frozen.

Coherence (CONTEXT.md glossary + the renderer seam): I deliberately did NOT mint a `LoadState` variant, because `LoadState` (renderer crate) is the backend's lifecycle truth (Idle/Started/Committed/Finished/Failed) and the SHELL's multi-stage resolution (name -> record -> content) happens BEFORE the backend's single `navigate` even starts — the backend has one lifecycle per underlying `ipfs://<cid>` load, so a name-resolution step is not a backend load-state. And I did NOT touch `TrustPosture`: loading/error are ORTHOGONAL to the trust posture (established by `chrome-loading-state-resets-trust-indicator` + `prominent-load-failure-and-ipns-resolution-diagnosis`; decision recorded there that a failure is not a trust posture). `LoadStep` is a THIRD, independent axis (progress), alongside `LoadState` (lifecycle) and `TrustPosture` (load path). Alternative considered: reuse `LoadState` and read the step from the URL bar / internal flags — rejected, it would conflate the shell's resolution stages with the backend's lifecycle and re-mean `LoadState`.

Layer: the step is set in `werust-core` (the toolkit-free shell), so all four edges read it from ONE fact (the chrome / chrome JSON), exactly as `is_loading()` and `trust_posture` already are. It only shows while loading; a settled/idle/failed chrome carries `Idle`.

Touches: `ChromeState` (new field, defaulted `Idle` — every existing `..ChromeState::default()` construction is unaffected); the FFI chrome JSON (`loadStep` field, new — additive, existing readers ignore it); the desktop status line + the mobile `statusLine()`; the platform-capability matrix (new `loading-progress` row).

## Decision 2 — transient-vs-hard is a PURE CLASSIFIER over the existing `last_error` reason, NOT a new error field the core plumbs through

USER-VISIBLE: introduces a retry affordance for the transient case (a new user-facing distinction). `last_error: Option<String>` stays the SINGLE source of truth (the honest, protocol-named reason from the resolver/decoder/fetch taxonomy — unchanged, never re-meaned). The transient/hard distinction is a pure function `ChromeState::failure_kind() -> Option<FailureKind>` (`Transient` | `Hard`) computed from that reason, mirroring how `is_loading()` derives from `load_state`.

Why classify the STRING, not a typed error: the failures that reach `last_error` come from TWO places — the shell's typed ENS/IPNS errors (set synchronously in core) AND the async content/render failures the webview reports as `LoadEvent::Failed { reason: String }` (a page-level `http` timeout, or the `ipfs://` scheme handler's `RendererError` string). The reason STRING is the only universal denominator across that seam (the webview hands back no typed error). So the classifier keys on the transient markers those reasons carry: a `timeout` / `timed out` / `transport error` / `connection` failure (the field finding's `transport error: timeout: global`, and the fetcher/provider `Transport`/`Io` taxonomy) is `Transient` (RETRYABLE — a reload re-runs the load, which the shell already supports incl. re-resolving a failed ENS name via `reload`); everything else (unsupported protocol, verification failure, malformed, invalid CID/target, hash mismatch, budget exceeded, no resolver / no contenthash) is `Hard` and KEEPS its prominent protocol-named reason verbatim.

Coherence: `FailureKind` is a NEW named concept but it does not overlap `TrustPosture` (a failure is not a trust posture — already settled) nor `LoadState::Failed` (that is the lifecycle fact; `FailureKind` is the retryability of the surfaced reason). It is a display-layer derivation, the same layer as `is_loading()` / the loading-wins precedence. Alternative considered: (a) thread a `retryable: bool` from every typed error site down into `ChromeState` — rejected, the webview `LoadEvent::Failed` path has no typed error to carry it, so the two paths would classify differently (incoherent); (b) a `TransientFailure` `TrustPosture` variant — rejected, re-means trust. Keying on the string keeps ONE classifier for BOTH paths.

Retry affordance: the transient error banner reads "timed out — reload to retry" and the chrome exposes `failure_is_retryable()` so each edge can show a retry control; the existing Reload button IS the retry (a transient ENS failure re-resolves from the pinned name, a transient content failure re-navigates). No new command/flag — retry reuses `reload`. Touches: the desktop `error_banner_text` + the mobile `errorBanner()` (transient vs hard wording), the FFI JSON (`failureKind` field, additive), the platform-capability matrix (new `retryable-error-distinction` row). Hard-failure wording/behaviour is UNCHANGED (keeps the protocol-named reason), so `prominent-load-failure` parity is preserved.

## Parity

Both surfaces are cross-platform parity capabilities (loading/error are, per the task). The Rust-testable half (the `load_step` + `failure_kind` facts reach every edge over the shared chrome / chrome JSON) is pinned by core + `ffi_json` tests. The one-line edge branches (desktop status/banner, mobile `statusLine()`/`errorBanner()`) read those same facts, exactly as the existing loading/trust/error branches do. Two matrix rows (`loading-progress`, `retryable-error-distinction`) are added `implemented` on all three platforms, at the same level `trust-indicator` / `prominent-load-failure` are.
