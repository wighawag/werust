# iOS: one reload/stop control, a loading spinner, and no history buttons

Task `ios-chrome-collapse-reload-stop-and-drop-history-buttons`, spec `chrome-conventional-controls` (stories 8-11). The decisions are in `DECISIONS.md` beside this file; this is what changed, what CI can prove, and what only a device could.

## What changed

`crates/werust-ios/App/Sources/WKWebViewShellController.swift`:

- The toolbar is `[reload/stop] [spinner] [URL field] [invalid badge] [⋮]`. The `◀` and `▶` are GONE (the WebKit edge-swipe is the iOS history affordance, and it covers BOTH directions), and the separate Reload and Stop buttons are ONE `reloadStopButton`. The URL field still hugs at `.defaultLow` while everything else hugs at `.required`, so it absorbs all the freed width.
- `refreshChrome` paints the control from the carrier and nothing else: `reloadStopButton.setTitle(chrome.reloadStopControlLabel, for: .normal)`, `reloadStopButton.accessibilityLabel = chrome.reloadStopControlDescription`, and the spinner's `alpha` + animation from one `spinnerVisible = chrome.loadSpinnerVisible`. The painter no longer reads the raw `chrome.loading` fact at all — the two lines that did (`stopButton.isEnabled = chrome.loading` / `reloadButton.isEnabled = !chrome.loading`) were the pre-collapse rule, and they are what the new guard forbids coming back, along with the two `canGoBack`/`canGoForward` enablement lines the buttons took with them.
- The control's TAP is `core.activateReloadStopControl()`: one core entry point that performs whatever the core's own mode says (see `DECISIONS.md` §3). Cancel is therefore still one tap, on the same control.
- The FIRST paint is the core's too (`initialChrome.reloadStopControlLabel` / `…Description`), so the control cannot start out wearing a mode the next refresh disagrees with.
- `webView.allowsBackForwardNavigationGestures = true` is untouched and is now the ONLY history affordance; its comment says so.

`crates/werust-ios/rust/src/lib.rs`: `CoreSession::activate_reload_stop_control` + the C-ABI export `werust_ios_activate_reload_stop_control`. `Sources/werust_mobile.h`: the matching declaration. `App/Sources/WerustCore.swift`: the binding method and the three new decoded chrome fields (not the mode's wire name — `DECISIONS.md` §4).

Nothing in `werust-core` changed: `can_go_back` / `can_go_forward`, the history seam and the chrome derivation are exactly as `reload-stop-collapse-and-loading-spinner-core-and-gtk` and `enable-the-ios-back-forward-swipe-gesture` left them. This edge only reads them.

## What CI proves

**The pure-Rust `verify` gate** (a plain `cargo test`, so it rides every change with no CI change), `crates/werust-ios/rust/tests/collapsed_control_and_dropped_history_buttons_shape.rs`:

- **Behaviour, headless and network-isolated.** `the_one_control_reloads_a_settled_page_and_stops_a_load_in_flight` drives a real `CoreSession`: settled → the mode is Reload → activating it starts a load → the mode is now Stop → activating it CANCELS the load (`LoadState::Idle`). That is the acceptance criterion "cancelling an in-flight load is still possible", asserted rather than argued. `the_history_capability_is_untouched_by_the_button_removal` pins that `can_go_back` / `can_go_forward` still track history in BOTH directions, which on iOS still have an affordance (the swipe).
- **The precondition.** `the_swipe_gesture_the_removal_rests_on_is_enabled_and_still_guarded` asserts the gesture flag is set in the painter AND that the sibling guard `back_forward_gesture_wiring_shape.rs` still carries its enablement, reporting and swipe-vs-button parity tests. Removing the buttons is only safe while that holds, so it reds this suite too, not only a file a reader might not open.
- **Source shape**, because the painter is Swift and this repo's gate has no Xcode: the two history buttons and their glyphs are gone; the toolbar arranges control → spinner → URL field → badge → ⋮; every painted value is a whole-statement assignment from the carrier; the painter never touches `chrome.loading` and never spells either mode's glyph or wire name; the tap goes through the one core entry point (and the header really declares it); and the mobile presentation guard's field lists are NOT registered yet (the MIGRATE/CONTRACT sequencing — since the CONTRACT step landed, that assertion reads the other way round and requires the registration).
- **Guards on the guard**: `the_assignment_check_is_not_satisfied_by_a_longer_field_name` (`chrome.reloadStopControl` is a prefix of both painted fields), `the_scanner_reads_literals_and_code_apart` (a glyph named in a doc comment is documentation, not an affordance), and the POSITIVE CONTROL inside `the_mobile_presentation_guard_field_lists_are_not_registered_here` (an already-registered field must be visible to the very check that asserts the new ones are absent, at both ends of the scanned file). That last test was inverted into `the_mobile_presentation_guard_registers_the_fields_this_edge_consumes` when the fan-in task `register-the-new-chrome-fields-in-the-mobile-presentation-guard` landed the registration.

**The `mobile-ios` leg** (`macos-14`, the only place in this project that compiles Swift at all) builds the Simulator `.app` and runs `docs/spikes/mobile-ios-shell-and-static-lib/check-app-bundle.sh`, which now asserts a LIST of required C-ABI symbols including `_werust_ios_activate_reload_stop_control` — the entry point the one control (and therefore cancel) rides on. So a Swift edge that stopped calling it, a header that lost the declaration, or a link that dropped the core fails there. The same script runs in the release job, so the shipped artifact is held to the same bar (`DECISIONS.md` §6).

**Mutation-checked.** Each of these turns the suite RED (verified, not asserted): painting the glyph from a Swift `"⟳"` literal instead of the carrier; the tap handler calling `core.reload()` itself; the spinner driven from `chrome.loading`; an on-screen `◀` added back to the toolbar stack; the gesture flag flipped to `false`; the spinner hidden with `isHidden` instead of keeping its slot; the accessible name dropped; the spinner left animating forever; the toolbar order shuffled; and — the sequencing mutation — registering `"loadSpinnerVisible"` in the mobile presentation guard's `DERIVED_FIELDS` early.

## Device verification (runtime-only, in NO gate, and NOT RUN)

The widgets themselves — that the glyph really flips mid-load, that the spinner really turns, that the row does not shift — need a running app on a simulator or a device. **NOT RUN, and not runnable here: there is no Mac on this project** (`work/notes/findings/apple-signing-tiers-and-the-no-mac-evidence-gap-2026-08-01.md`). These steps are recorded for whoever next has one, not as a run of record. Build + launch: `crates/werust-ios/build-and-run.sh` on a Mac with Xcode.

1. **The toolbar has two buttons.** Launch. EXPECT: a reload glyph, a (still, invisible) spinner slot, a wide URL field, and the ⋮ menu. No `◀`, no `▶`.
2. **The control flips and cancels.** Navigate to a slow page. EXPECT: mid-load the control shows the stop glyph and the spinner turns; tapping it CANCELS the core's load (the status line stops naming a phase, the progress line fades, the spinner stops, the control returns to the reload glyph). Tapping it on a settled page reloads. NOTE the known pre-existing gap here: `core.stop()` does not call `webView.stopLoading()`, so the platform load keeps running underneath (`work/notes/observations/ios-stop-does-not-stop-the-wkwebview-2026-08-04.md`, `DECISIONS.md` §7).
3. **The row never shifts.** Watch the URL field's left edge across a whole load and settle. EXPECT: it does not move — the spinner's slot is reserved whether or not it is turning.
4. **The pre-content window spins.** Navigate to a bare `.eth` name (e.g. `ronan.eth`). EXPECT: the spinner turns during the ENS/IPNS resolve, BEFORE the progress bar has anything to report, and the control is still in its reload mode there (nothing to stop yet — the deliberate split in `reload-stop-collapse-and-loading-spinner-core-and-gtk`'s decision 1).
5. **The swipe still navigates history.** Follow a link so there are two entries, then swipe from the left edge, and again from the right. EXPECT: back and forward both navigate, and the URL bar, trust badge and error banner describe the page landed on. This is the affordance the removed buttons were traded for; its own steps are in `docs/spikes/enable-the-ios-back-forward-swipe-gesture/`.
6. **VoiceOver.** Focus the control. EXPECT: it announces the core's description ("Reload this page" / "Stop loading this page", following the mode), and the spinner is skipped rather than announcing a second, unlabelled progress indicator (`DECISIONS.md` §2).
