# Spike: the `EthereumProvider` seam + trusted `RpcProvider` backend

Durable evidence + decisions for task `ethereum-provider-seam-and-trusted-rpc-backend` (spec `ens-to-ipfs-resolution-phase1-rpc-skeleton`, story 5).

## What was built

- The `EthereumProvider` seam (trait) in `crates/werust-core/src/ethereum.rs`: `eth_call(&self, call: &EthCall) -> Result<Vec<u8>, ProviderError>`. `EthCall` is `{ to, data, block }` (address + ABI-encoded calldata + a `BlockTag`); the method returns the raw (ABI-encoded) return bytes. This is werust's INTERNAL trusted-read seam that ENS resolution calls, modelled exactly like the sibling `Fetcher` / `ContentSource` / `Renderer` seams (the interface is the abstraction; the trust level is a swappable backend). It is DISTINCT from the page-injected `EIP-1193 provider` (`crate::provider`), and the module docs say so.
- `RpcProvider`, the ONE Phase-1 backend: a TRUSTED plain JSON-RPC `eth_call` skeleton. It builds the JSON-RPC envelope, POSTs it over an `RpcTransport`, and decodes the `0x`-hex `result` into bytes, surfacing every failure as a typed `ProviderError`.
- `RpcTransport` (trait) + `UreqRpcTransport` (default backend): the minimal synchronous JSON-RPC HTTP POST, binding `ureq`'s POST behind a narrow seam. The endpoint is user-overridable with a labelled default (`DEFAULT_RPC_ENDPOINT` + `RpcProvider::new` / `with_endpoint`), mirroring `GatewayContentSource::new` / `with_gateway` — no config subsystem.
- Seam-contract tests (in `ethereum.rs`, off the live network): the decoded-return-bytes happy path; an assertion that the OUTGOING request carried the `eth_call` JSON body (method + params) via a capturing in-process transport double; a pinned-block-number hex quantity; a JSON-RPC error object surfaced as `ProviderError::Rpc`; a transport failure; an unparseable result refused (never empty bytes); the empty `"0x"` result decoding to zero bytes; and an END-TO-END test over the BOUND `UreqRpcTransport` against a `127.0.0.1:0` loopback fixture that ALSO asserts the fixture received the `eth_call` JSON over the wire; plus a non-2xx-is-a-transport-error case.

## Reproducing

```sh
cargo test -p werust-core --lib ethereum
```

All nine tests run headless against in-process doubles + a `127.0.0.1:0` loopback server the test stands up and tears down (no internet).

## Drift re-check (per WORK-CONTRACT.md "Drift is a needs-attention signal")

Confirmed against current `crates/fetcher/src/lib.rs`: the `Fetcher` seam is STILL GET-only (`fetch(&self, url) -> Result<Response, FetchError>`, no method/body; `HttpFetcher` does `agent.get(url).call()`; `GatewayContentSource` only builds a GET URL). The task's transport premise holds; no drift.

## Decisions

- **Transport path (b): `RpcProvider` binds its OWN minimal sync JSON-RPC POST transport, NOT an extended `Fetcher` seam.** The task allowed either (a) extend the `Fetcher` seam with a body-carrying POST method, or (b) bind a minimal transport inside this backend. Chose (b). Rationale: extending `Fetcher` would widen a SHARED seam's surface (adding a POST-with-body method to a trait every fetch path implements) for a SINGLE consumer, touching `HttpFetcher` plus every `Fetcher` impl/test double in the tree; (b) keeps the change scoped to this one new module. The transport is still BOUND, not hand-rolled (`UreqRpcTransport` binds `ureq`'s POST exactly as `HttpFetcher` binds its GET), still off any async runtime, and still behind a seam (`RpcTransport`), so nothing leaks. **Touches:** only the `ethereum` module + `werust-core`'s dependency set (adds `ureq = "=3.3.0"`, the same client the `fetcher` crate already binds; TLS never hand-written). The `Fetcher` seam is left untouched. If a second POST consumer appears later, promoting a shared POST transport is a clean follow-up, not a rewrite.
- **`RpcTransport` is its own seam (not an inline `ureq` call).** Making the transport a trait double-purposes it: it keeps the bound HTTP client behind a seam (house style), AND it lets tests substitute an in-process transport double that CAPTURES the outgoing request body — the mechanism that proves the `eth_call` JSON (method + params) was actually sent, so a GET-only/body-dropping transport could not pass. The end-to-end test additionally exercises the REAL `UreqRpcTransport` against a loopback fixture that records the wire body.
- **Seam signature shaped for a later async backend (Phase 2).** `eth_call` returns OWNED `Vec<u8>` by value (no borrow tied to a sync call stack) and takes `&self` (shared, so a connection-pooling async client with interior mutability fits). A Phase-2 async (tokio) backend can drive its async client to completion internally (`block_on` bridged AT this boundary) and return the owned result; nothing structurally blocks the swap. Documented at the seam.
- **Block tag is a first-class `BlockTag` enum, default `Latest`.** `eth_call` names the block it reads at. ENS reads current state, so `BlockTag::Latest` (serialized `"latest"`) is the default via `EthCall::new`; `BlockTag::Number(u64)` pins a block (serialized as the `0x`-hex quantity the JSON-RPC spec requires). A small enum (not a bare string) stops a caller passing a mistyped tag while leaving room to grow (e.g. a future `Finalized`). This is a user-visible default (`latest`), recorded here + at the choice site.
- **JSON-RPC error mapping.** A response is decoded into EITHER a `result` (the `0x`-hex bytes) or an `error` object, never both. An `error` object -> `ProviderError::Rpc { code, message }` (the endpoint's OWN code/message, so the caller sees the RPC's reason, e.g. a revert). A transport/connection failure or a non-2xx HTTP status -> `ProviderError::Transport` (the call never got a well-formed answer). A reachable-but-malformed answer (not JSON, neither/both of result+error, a non-`0x`/odd-length/non-hex result) -> `ProviderError::Decode` (refused, never returned as empty bytes). A request bad before it is sent -> `ProviderError::InvalidRequest`. `"0x"` is a genuine empty return and decodes to zero bytes (distinct from a decode failure). Every failure is a typed error, never a panic, never a silent empty success.
- **Labelled default endpoint (`DEFAULT_RPC_ENDPOINT`), TRUSTED.** `RpcProvider::new` uses a public keyless mainnet RPC as a sensible default — NOW `https://1rpc.io/eth` (updated by task `configurable-rpc-endpoint-via-env`, which also added the `WERUST_RPC_URL` env override, read once at session construction; the default at the time of THIS spike was `https://ethereum-rpc.publicnode.com`, later observed DNS-/TLS-blocked on home networks); `with_endpoint` overrides it outright. This is a TRUSTED origin (the `eth_call` result is taken on its word — Phase 1 has no light client), so an ENS-resolved page is labelled "content-verified, name via TRUSTED RPC" upstream, never "verified". The durable endpoint policy is not this task's concern; the trustless backend is the Phase-2 swap behind the same seam. Mirrors the `GatewayContentSource` default-constant + constructor-override shape; no config subsystem.
