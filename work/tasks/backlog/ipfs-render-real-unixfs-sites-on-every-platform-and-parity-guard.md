## Open questions

These are genuine forks a human must settle before this can be built autonomously; they change the shape of the work.

1. **Trustless-DAG retrieval vs gateway-assembled bytes — how far do we go in THIS task?** The desktop hash-mismatch (below) is caused by verifying reassembled UnixFS content against a `dag-pb` root CID that names the DAG's root BLOCK, not the reassembled payload. There are two honest fixes and they differ enormously in size:
   - **(a) Verifiable retrieval (the real fix):** fetch the CAR / raw blocks (trustless-gateway `?format=car` or block-by-block `?format=raw`), walk the `dag-pb`/UnixFS DAG, verify EACH block against its own CID, and reassemble the file/directory LOCALLY. This is the only way the "hash-verified" trust claim is actually TRUE for a real site. It is also exactly the "trustless retrieval / verifiable IPFS" work the roadmap DEFERRED to an exploration spec (`docs/adr/0001`, and the T1 spec's "deferred, carried on the exploration spec"). If we pick (a), this task should probably SPAWN a dedicated exploration/task for the DAG-walk+CAR verifier and depend on it, rather than inline a large crypto-retrieval subsystem here.
   - **(b) Honest relabel + scoped support:** keep single-block verified rendering working, but for a multi-block UnixFS CID either (i) fetch from a gateway and render it under a DISTINCT, honest posture that does NOT claim byte-verification (e.g. "served via gateway, name via trusted RPC" — NOT "content-verified"), or (ii) fail closed with a clear "verifiable multi-block retrieval not yet implemented" message. This keeps Phase-1's trust honesty intact without building the DAG walker now.
   - DECIDE: (a) now, (a)-as-a-spawned-exploration-task-this-depends-on, or (b-i)/(b-ii) now with (a) filed as a follow-on. The trust-honesty rule (never call something "verified" that was not byte-verified) is NON-NEGOTIABLE in every branch.
2. **Mobile `ipfs://` interception mechanism — confirm the platform APIs.** Android needs `WebViewClient.shouldInterceptRequest` (or a `WebViewAssetLoader`-style path) routing `ipfs://` into the SAME `werust-core` resolve/verify path the desktop `install_ipfs` uses; iOS/WKWebView needs a `WKURLSchemeHandler` registered for `ipfs`. Confirm both are viable for a custom (non-http) scheme on a System WebView / WKWebView, and that the Rust core's resolve path can be called from the OS edge the same way on all three. (Android's System WebView may restrict custom top-level schemes; if so, the fallback is an `https://appassets`/`WebViewAssetLoader` internal origin that the core maps to `ipfs://` internally — decide which.)
3. **Where does the parity guard live and how strict is it?** You asked for a STRONG mechanism ensuring every feature is either implemented in ALL contexts (desktop, iOS, Android) or has a tracked task (an exploration task if needed) so nothing is forgotten. DECIDE the mechanism (see "The parity guard" below): a capability MATRIX (checked-in, one row per cross-cutting capability x {desktop, ios, android} = implemented / stubbed+task-linked / n-a) enforced by a `verify`-time test that FAILS if any cell is a bare unimplemented stub with no linked follow-on task; and/or an ADR establishing the rule that a seam method must not be silently no-op'd on any backend. Confirm the shape before building.

## What to build

Typing a real `.eth` name (e.g. `mandalas.eth`) must actually RESOLVE AND RENDER its immutable IPFS site on EVERY werust context we ship — desktop (WebKitGTK), iOS (WKWebView), and Android (System WebView) — or fail closed with an honest, legible reason. Today the ENS resolution half works (the name resolves to a real `ipfs://<cid>` on all platforms), but the `ipfs://` RENDER half is broken in two distinct ways, and the Phase-1 tests missed both because they only ever exercised offline fixtures / single-block CIDs and the desktop handler in isolation — never a real UnixFS site through a real mobile WebView.

**Defect A — desktop verifies the wrong bytes for a real (multi-block) site.** The verified `ipfs://` path (`VerifyingContentFetcher` over `GatewayContentSource`) fetches `<gateway>/ipfs/<cid>` and re-hashes the WHOLE response with SHA-256, comparing against the CID's multihash. That only holds for a single-block `raw`/leaf CID. A real site is a CIDv1 `dag-pb`/UnixFS DAG (the failing CID `bafybei...` decodes to version=1, codec=0x70 dag-pb, sha2-256): the gateway returns the REASSEMBLED content, whose bytes do NOT hash to the `dag-pb` ROOT-BLOCK CID, so every real site fails `HashMismatch`. Resolve this per open-question 1 (verifiable DAG/CAR retrieval, or an honest relabel/fail-closed), NEVER by relaxing the trust claim silently.

**Defect B — mobile has no `ipfs://` handler at all.** The `ipfs://` scheme handler (`install_ipfs` -> `register_uri_scheme`) is WebKitGTK-desktop-only. The Android Rust backend's `register_scheme_handler` is an empty no-op and the Kotlin `WebViewClient` has no `shouldInterceptRequest`; iOS has no `WKURLSchemeHandler`. So on mobile a resolved `ipfs://<cid>` reaches a bare Chromium/WKWebView that returns `net::ERR_UNKNOWN_URL_SCHEME`. Wire real `ipfs://` interception on both mobile edges, routing into the SAME `werust-core` resolve+verify path desktop uses (per open-question 2), so the SAME trust posture and fail-closed behaviour apply everywhere.

**The parity guard (the durable mechanism you asked for).** This defect existed because a seam method (`register_scheme_handler`) was silently no-op'd on the mobile backend and nothing caught it: a capability shipped desktop-only with no trace. Build a mechanism so this cannot happen silently again (per open-question 3): a checked-in capability matrix (one row per cross-cutting user-facing capability, columns desktop/ios/android, each cell one of implemented / stubbed-with-linked-follow-on-task / not-applicable) plus a `verify`-time guard that FAILS the gate if any capability is unimplemented on a platform WITHOUT a linked tracked task, and/or an ADR making "a seam method may not be silently no-op'd on any backend — stub must be explicit and task-linked" a standing rule. The intent: every feature is either implemented in all contexts, or has a task (exploration task if needed) tracking its completion, so nothing is forgotten.

## Acceptance criteria

- [ ] A real multi-block UnixFS `.eth` site (e.g. `mandalas.eth` -> its `bafybei...` dag-pb CID) renders end to end on DESKTOP (WebKitGTK), OR fails closed with an honest, legible reason under a posture that does NOT falsely claim byte-verification — whichever branch of open-question 1 is chosen. The current `HashMismatch`-on-every-real-site behaviour is gone.
- [ ] The chosen trust posture is HONEST: nothing is ever labelled "content-verified" / "verified" unless its bytes were actually verified against the CID (single-block direct, or every block of the DAG in the verifiable-retrieval branch). A gateway-assembled, non-byte-verified render (if that branch is chosen) is a distinct, honestly-labelled posture, never "verified".
- [ ] `ipfs://` is intercepted and routed through the `werust-core` resolve+verify path on ANDROID (System WebView) and iOS (WKWebView), not just desktop; a resolved `ipfs://<cid>` no longer yields `net::ERR_UNKNOWN_URL_SCHEME`. The mobile backend's scheme registration is no longer a silent no-op.
- [ ] The SAME fail-closed behaviour and trust posture apply on all three platforms (an unsupported/unverifiable/failed load shows the same honest chrome reason everywhere; the ENS-origin "name via trusted RPC" posture is preserved through the real mobile render).
- [ ] A platform-capability parity guard exists and is enforced by `verify`: it FAILS if a cross-cutting capability is unimplemented on any of {desktop, ios, android} without a linked tracked task. The `ipfs://` render capability is recorded in the matrix as implemented (or explicitly stubbed-with-task) per platform.
- [ ] An integration/e2e-style test exercises the REAL render path per platform as far as each platform's harness allows (at minimum: the desktop real-webview `ipfs://` path against a multi-block fixture that mirrors a real UnixFS layout, and a mobile-edge test that proves `ipfs://` is intercepted and reaches the core rather than erroring at the WebView). The gap that hid these bugs (no test drove a real UnixFS site through a real WebView) is closed.
- [ ] Tests cover the new behaviour (mirror the repo's existing test style) and are network-isolated (pinned fixtures / loopback, no live gateway or live RPC in the gate).
- [ ] If this task makes code write to a SHARED / GLOBAL location, tests isolate it and assert the real one is untouched. (Likely N/A here, but honour it if a block store / cache dir is introduced.)

## Prompt

> Goal: make a real `.eth` name render its real immutable IPFS site on EVERY werust context (desktop WebKitGTK, iOS WKWebView, Android System WebView), or fail closed with an honest reason, and install a durable parity guard so a capability can never again silently ship on one platform only. The ENS resolution half already works everywhere (the name resolves to a real `ipfs://<cid>`); this task fixes the `ipfs://` RENDER half, which is broken two ways, and closes the test-coverage gap that hid both.
>
> Domain vocabulary: an `ipfs://<cid>` where the CID is CIDv1 `dag-pb` (codec 0x70) is a UnixFS DAG — a root block that LINKS to child blocks (chunked file, or a directory listing), NOT a single blob. A trustless gateway returns either the reassembled content (`?format=<mime>` / default) OR the raw blocks / a CAR (`?format=raw` / `?format=car`). Byte-verifying a UnixFS site means walking the DAG and checking EACH block against its own CID, then reassembling locally — re-hashing the reassembled payload against the root CID does NOT work (that is the desktop `HashMismatch` bug). A single-block `raw` (0x55) CID is the only case where "hash the whole response == the CID" holds; the current verifier only supports that.
>
> Where to look: the desktop `ipfs://` handler is `install_ipfs` in the webview backend (`register_uri_scheme` on the WebKitGTK `WebContext`), routing into `werust_core::ipfs::resolve_ipfs_request` over `VerifyingContentFetcher` + `GatewayContentSource` (the verifier lives in the `fetcher` crate and re-hashes with SHA-256). The mobile backends are `crates/werust-android` (Rust `backend.rs` whose `register_scheme_handler` is an empty no-op; Kotlin `BrowserActivity.kt` whose `CoreWebViewClient` has no `shouldInterceptRequest` and just `webView.loadUrl(...)`) and `crates/werust-ios` (no `WKURLSchemeHandler`). The ENS front door + trust postures landed in the Phase-1 tasks in `work/tasks/done/` (`bare-eth-urlbar-front-door-end-to-end`, `name-via-trusted-rpc-trust-state`) — reuse `NameViaTrustedRpc` and the fail-closed chrome; do NOT reintroduce a "verified" label for anything not byte-verified.
>
> Trust honesty is the non-negotiable invariant (spec `ens-to-ipfs-resolution-phase1-rpc-skeleton`, `docs/adr/0001`): the whole point of werust is that "content-verified" MEANS the bytes were checked against the hash. So the multi-block fix must EITHER actually verify every block of the DAG (verifiable retrieval) OR render under a distinct, honestly-labelled non-verified posture / fail closed — never silently call a gateway-assembled page "verified". Pick the branch per the open questions; if you choose full verifiable retrieval, prefer spawning a dedicated exploration/task for the DAG-walk+CAR verifier and depending on it rather than inlining a large retrieval subsystem here (the roadmap already earmarked "trustless retrieval" for an exploration spira).
>
> The parity guard is the durable deliverable, not an afterthought: this bug happened because a seam method was silently no-op'd on one backend with nothing to catch it. Build the mechanism agreed in open-question 3 (a checked-in capability matrix x platform, `verify`-enforced so an unimplemented-without-linked-task cell reds the gate; and/or an ADR forbidding silent no-op seam impls). It must make "feature X is desktop-only and nobody noticed" impossible to ship silently again.
