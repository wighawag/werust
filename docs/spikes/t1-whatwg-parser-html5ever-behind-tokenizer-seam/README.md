# Spike: html5ever behind the parser seam (T1 real WHATWG parse)

Durable evidence + decisions for task `t1-whatwg-parser-html5ever-behind-tokenizer-seam` (spec story 13, `docs/conformance-tiers.md` T1).

## What was built

The parse half of conformance tier **T1**: a real WHATWG-algorithm HTML parser (html5ever) bound behind the native renderer's front-end seam, so REAL documents (not just the fixed v0 allowlist) parse into werust's `Dom` and feed the SAME cascade/layout/paint path unchanged. In `crates/native-renderer/`:

- **`parser.rs` — the `Parser` seam** (`parse(source) -> ParsedDocument { dom, author_css }`). This is the whole-front-end swap point the conformance ladder calls the `Tokenizer | TreeBuilder` seam. `SubsetParser<T, B>` packages the existing T0 pair (`SubsetTokenizer` + `AllowlistTreeBuilder`) behind it unchanged (recovering author CSS from the token stream, as T0 always did). `ParsedDocument` carries the author CSS alongside the tree so the pipeline is uniform across parsers.
- **`html5ever_parser.rs` — `Html5everParser`** (the T1 parser). Runs html5ever over the source into the standard `RcDom`, then converts that `Rc<Node>` tree into werust's owned `Dom`. It drops nothing by element name (a real `<article>`/`<table>`/`<nav>` is kept — the point of T1), lowercases tag/attr names to match the rest of the pipeline, and recovers author CSS by walking the `<style>` elements html5ever keeps in the tree.
- **`pipeline.rs`** now wires `render_with(parser: &dyn Parser, source, viewport_width)` — parse → cascade → flow → software text — so swapping T0 for T1 is a one-line parser change with cascade/layout/paint untouched.
- **`backend.rs`** — the `NativeRenderer` `Renderer`-seam backend now parses with `Html5everParser`, so the native render path consumes the html5ever-produced tree.

## Reproducing

```sh
cargo test -p native-renderer
```

The T1 evidence: `html5ever_parser::tests` (a minimal fragment gains the full `html>head/body` scaffold; elements off the v0 allowlist like `<article>`/`<table>` with the implied `<tbody>` are kept; mis-nested `<b>/<i>` recover the WHATWG way; named + numeric entities decode; comments/doctype are dropped from the render tree); `pipeline::tests::same_pipeline_renders_via_the_t1_parser_swap` (the seam swap is the only change, cascade/layout/paint still paint the styled content); `pipeline::tests::t1_parser_renders_a_real_document_off_the_v0_subset` (a real `<!doctype>` document with semantic elements, an author `<style>`, and `&copy;`/`&amp;` entities parses and paints end to end). The T0 golden fixtures still pass byte-for-byte through the html5ever-backed backend, confirming the swap is transparent to downstream.

## Decisions

- **Bind html5ever at a whole-front-end `Parser` seam, NOT at the literal two-trait `Tokenizer` + `TreeBuilder` split.** A real WHATWG parser fuses tokenizing and tree construction (they share insertion-mode / open-element / raw-text state, the adoption agency, foster parenting), so html5ever CANNOT consume a pre-tokenized `Token` stream — it does not factor at the T0 boundary. The load-bearing seam invariant was never "there are exactly two traits"; it is **"everything downstream consumes the `Dom`"** (stated verbatim in the T0 `tokenizer.rs`/`tree.rs`/`lib.rs` docs). So I introduced `Parser` (`source -> ParsedDocument`) as the swap point, kept the T0 `Tokenizer`/`TreeBuilder` traits as the subset implementation (composed behind `SubsetParser`), and slotted html5ever in as a second `Parser`. **Alternative considered (rejected):** hand-write a `markup5ever::TreeSink` that emits our `Dom` directly and feed it html5ever's own tokenizer, keeping a token-shaped seam. Rejected because html5ever's tokenizer is not separable from its tree builder for correct WHATWG behaviour, and a hand-rolled `TreeSink` (interior-mutable handles, reparenting, foster parenting) is exactly the dangerous, easy-to-get-subtly-wrong code the thesis says to bind, not write. **Coherence:** `Parser` names the seam the glossary already calls "the `Tokenizer | TreeBuilder` seam" and the tiers doc already assigns to "html5ever for parse"; it does not re-mean or duplicate an existing concept — it names the umbrella the two T0 traits already jointly form. **Touches:** `render_with`'s signature (now `&dyn Parser` instead of the tokenizer+tree_builder pair) and every caller (backend, pipeline tests); the sibling `t1-core-css-stylo-and-latin-shaping-parley` and `t1-wpt-subset-regression-meter` tasks consume the `Parser`/`Html5everParser` surface.

- **`ParsedDocument` carries author CSS next to the `Dom`; the two parsers recover it from different places.** T0's allowlist builder DROPS `<style>` (off the v0 element allowlist), so `SubsetParser` reads author CSS from the token stream (as the T0 pipeline always did). html5ever KEEPS `<style>` in the tree, so `Html5everParser` walks the produced `Dom` for `<style>` text. Returning both from `parse` keeps the pipeline uniform and stops it caring HOW the CSS was recovered. `<style>` never paints on either path: the UA sheet sets `head { display: none }` and `<style>` lives under `<head>`. **Alternative considered (rejected):** keep the pipeline's old token-stream `extract_author_css` and skip it for T1, branching the pipeline per parser — rejected because it re-introduces a front-end-shaped concern into the (now parser-agnostic) pipeline. **Touches:** the cascade input; the sibling stylo task will likely replace this whole author-CSS extraction, at which point `ParsedDocument.author_css` is the seam it swaps at.

- **Use the standard `markup5ever_rcdom::RcDom` as the intermediate, then convert to werust's owned `Dom`.** `RcDom` is the reference DOM html5ever's own test suite drives, so binding it is low-risk and its tree is already correct WHATWG output; the conversion to our simple owned `Dom` (elements + text, dropping Document-wrapper/doctype/comments/PIs a static render does not consume) is a small, testable recursive walk. `markup5ever_rcdom` is published as `0.39.0+unofficial` ("unsupported DOM for html5ever/xml5ever tests"); it is used ONLY inside `html5ever_parser.rs` and never leaks past the `Parser` seam (the seam surface is our own `Dom`), so it is swappable later (e.g. for a bespoke `TreeSink` or a different backing DOM) with no downstream change. **Touches:** only `native-renderer`'s dependency set (`html5ever`, `markup5ever_rcdom`); nothing past the seam.

## Notes

- The T0 golden fixtures render identically through the html5ever-backed backend, which is the intended transparency of the swap (downstream is untouched). This is asserted by the existing `t0_server_floor_goldens` suite continuing to pass, not by any change to the goldens.
- AC "the WPT tree-construction subset can be run against it": `Html5everParser::new().parse(source) -> ParsedDocument` is the public, runnable surface a WPT tree-construction harness drives; the threshold + harness itself is the sibling task `t1-wpt-subset-regression-meter`.
