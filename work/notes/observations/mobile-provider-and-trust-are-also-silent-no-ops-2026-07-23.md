# Mobile EIP-1193 provider injection and trust indicator are ALSO silent no-ops (not just `ipfs://`)

2026-07-23, spotted while seeding the platform-capability-parity guard (`platform-capability-parity-guard`).

The parity-guard task's settled seed listed **EIP-1193 provider injection** and **trust indicator** as `implemented` on all three platforms. Against current code that is NOT true: on BOTH mobile backends (`crates/werust-android/rust/src/backend.rs`, `crates/werust-ios/rust/src/backend.rs`) `register_script_message_handler` and `inject_script` are empty `{}` no-ops, and neither backend overrides `trust_posture` / `trust_hooks` / `mark_ens_origin` (they inherit the seam defaults: `UnverifiedOrigin`, `TrustHooks::none()`, no-op). Only the desktop `webview-renderer` backend wires them (`install_provider`, the shared `LoadLifecycle` posture). So provider injection and the trust indicator are desktop-only today, exactly the same silent-no-op class as the `ipfs://` gap the guard exists to catch.

The guard now seeds these two rows truthfully as desktop-`implemented`, iOS/Android-`stubbed`, linked (like the `ipfs://` row) to `mobile-ipfs-scheme-interception-ios-and-android` as the mobile-webview-integration follow-on. NOTE: that follow-on task's body is scoped to `register_scheme_handler` / `ipfs://` interception specifically; it does NOT explicitly cover the provider bridge or the trust-posture wiring on mobile. A human may want a dedicated mobile task (e.g. `mobile-provider-injection-and-trust-indicator`) so each stubbed cell links to a task that genuinely covers ITS completion, rather than folding three capabilities under one ipfs-scoped slug. Recorded in `docs/adr/0005-*` (the guard's design) and the done record.
