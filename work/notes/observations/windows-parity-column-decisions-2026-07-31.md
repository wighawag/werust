# Decisions taken while filling the `windows` parity column (2026-07-31)

Task `windows-parity-column-and-stub-tasks`. Four judgement calls the task did not settle, recorded here so a reviewer can ratify or reverse them rather than reverse-engineer them. Each is visible in `docs/platform-capability-matrix.toml`'s per-row prose too; this note is the one place they sit together. The sibling `macos-parity-column-decisions-2026-07-31.md` is the precedent this column was filled against, and the first two decisions below are deliberately the same calls made the same way.

## 1. `follow-os-color-scheme` is `stubbed`, pointing at the PACKAGING task

Windows does more here than macOS does and is still the one row marked short. The page half is genuinely wired (`SetPreferredColorScheme(…AUTO)` on the WebView2 profile, so `prefers-color-scheme` and UA-styled controls follow the OS and werust forces nothing) and the chrome half reads the OS setting through the engine crate's one registry read, mapped by the shared `renderer::OsColorScheme` rule, re-read on `WM_SETTINGCHANGE`. What is missing is the application MANIFEST: without a comctl32 v6 dependency the chrome draws classic-styled and its system-drawn push BUTTONs ignore dark mode entirely, so a dark-mode Windows shows dark chrome surfaces with light buttons.

Marked `stubbed` rather than `implemented`-with-a-caveat on the macOS column's decision 1 (a partly-wired capability is stubbed, not green with a caveat), and because `windows-release-packaging-leg` — the task that owns the manifest — itself calls this "a visible ADR-0009 gap that no code change in the window can close". ADR-0009 is the decision this row encodes, so a green cell would claim a capability whose failure a user meets on the first dark-mode machine.

Alternative considered: `implemented`, on the reading that this row's DESCRIPTION names only the page (`prefers-color-scheme` and UA-styled controls), which really does follow. Rejected as the reading that flatters the column; if a reviewer prefers it, this is the cheapest of the four decisions to reverse (one cell, one comment).

Also considered and rejected: cutting a new `windows-chrome-visual-styles-manifest` task for the cell to point at. That would FORK work `windows-release-packaging-leg` already owns and scopes (the manifest plus the by-hand re-check CI cannot do), which is the duplication the coherence check exists to prevent. What it touches: that task now carries one extra acceptance criterion — flip this cell when the manifest lands and the manual check confirms — so the stub cannot rot silently after its work is done.

## 2. Two `stubbed` cells got NEW tasks; both are Windows twins of open macOS tasks

`mutable-name-tofu-bless` (the Win32 trust indicator is a `STATIC` with no click target, so there is nowhere to put the bless action) and `debug-capture-console-and-network` (the only network capture point is the shared injected `fetch`/`XHR` shim, so there is no main-document row and no row for the requests werust's own scheme handler serves) are both real, wire-level gaps. They are authored as `windows-trust-surface-bless-affordance` and `windows-debug-network-capture-main-document-and-scheme-handled`, mirroring the macOS slugs deliberately.

Alternative considered: ONE task per gap covering both new desktop windows, since they share `crates/desktop-paint` and the macOS twins are still open in backlog. Rejected because the shared half is already shared and the missing half is entirely per-toolkit (a `TrackPopupMenu`/owner-drawn popup vs an AppKit surface; `AddWebResourceRequestedFilter` vs a `WKURLSchemeHandler` capture point), and because ADR-0005's linkage nuance asks each stubbed cell to name a task that genuinely covers ITS completion. Each of the four task bodies names its sibling and says the second to land must reuse the rule rather than fork it, and must not change the other edge by accident. What it touches: `crates/desktop-paint` (the shared carrier both windows read) and the two macOS backlog tasks.

## 3. `implemented` where the evidence is wiring plus the shared core, not a driven runtime step

Several Windows cells are green on compilation + the source-shape guard + the shared core's own tests, because the `windows-latest` smokes drive one hash-verified `ipfs://` load and no runner clicks, types, presses Back or serves a `_redirects` fixture: `spa-url-tracking`, `back-forward`, `retrieval-backend`, `scheme-less-entry-routing`, `blank-window-open-navigates-in-place`, `ipfs-web-pathing-fallback`, `ipfs-redirects-3xx-navigation`. Each says so in its own comment, in the same words the macOS column uses for the same situation, so the distinction is visible per row and not only here. Using `stubbed` for "wired but unwitnessed" would blur it into a verification tracker (macOS decision 2), and the honest home for the unwitnessed half is the row's prose plus the manual steps in `docs/spikes/windows-win32-window-and-chrome/README.md`.

The task's own instruction — do not mark a rendering / input / focus / HiDPI-dependent row `implemented` on the strength of a CI run — is respected: no capability ROW in this matrix names rendering quality, input routing, focus or HiDPI, and the rows that come closest are handled as above (`follow-os-color-scheme` stubbed; `loading-progress` green only because the runner measured the page rectangle rather than judging pixels; the debug view's ROW COLOURS called out as an unverified claim about pixels in its own comment).

## 4. Column placement, and the guard's expected list

`windows` sits BESIDE `macos` in `platforms` (and its cell line directly under each row's `macos` line), so the three desktop edges read together — the slot the macOS column left for it. The guard's `the_real_matrix_is_well_formed_and_covers_every_platform` now also expects `windows`, for the same reason it expects `macos`: a later change cannot drop the column and take its three tracked gaps with it. That strengthens the guard; nothing about it was weakened. The `desktop`-means-Linux naming wrinkle is now sharper (three desktops, one of them called `desktop`) and is left where it was recorded, `desktop-platform-key-now-means-linux-only-2026-07-31.md`; the matrix header note is updated to say three rather than two, but the rename is still a human's call with other owners.
